Chapter 15: Command Comparisons

Linux offers multiple tools that seem to do similar things. Knowing when to use which is what separates a proficient user from someone who just memorizes commands. This chapter puts frequently confused commands side by side so you can see exactly how they differ and when to reach for each one.

How to Read This Chapter

Each section contains a summary, a comparison table, use-case recommendations, and examples. Bookmark the tables — they make excellent quick-reference material.

1. cp vs mv

Summary: cp creates a duplicate of a file (the original remains). mv relocates or renames a file (the original is gone from its old location).

Featurecpmv
What it doesCopies files (original stays)Moves or renames files (original removed)
Disk usageDoubles the space usedNo extra space (on same filesystem)
Speed (same disk)Slow for large files (copies data)Instant (just changes directory entry)
Speed (across disks)Slow (copies data)Slow (copies then deletes original)
Preserves originalYesNo
Can renameYes (copy with new name)Yes (primary way to rename)
Recursive flag-r (required for directories)Works on directories by default
Safe flag-i (interactive), -n (no clobber)-i (interactive), -n (no clobber)

When to Use Each

  • Use cp when you need the file in two places, when creating a backup, or when you want to keep the original safe.
  • Use mv when you want to rename a file, reorganize files into different directories, or move files without using extra disk space.

Examples

$ cp report.txt report_backup.txt     # Create a backup copy
$ cp -r /project /project_backup       # Copy an entire directory

$ mv report.txt final_report.txt       # Rename a file
$ mv report.txt /archive/              # Move to another directory
$ mv old_name/ new_name/               # Rename a directory
Tip

If you want to move a file but keep a backup, do both: cp file.txt file.txt.bak && mv file.txt /new/location/

2. grep vs find

Summary: grep searches inside files for text patterns. find searches the filesystem for files by name, size, date, permissions, and other attributes.

Featuregrepfind
SearchesFile contentsFile names, attributes, metadata
InputText / file contents / stdinDirectory tree
Pattern typeRegular expressionsGlob patterns, conditions
Answer to"Which files contain this text?""Where is this file?"
Recursivegrep -rRecursive by default
Can execute commandsNo (use with xargs)Yes (-exec)
Filter by sizeNoYes (-size)
Filter by dateNoYes (-mtime, -newer)
Filter by typeNoYes (-type f, -type d)

When to Use Each

  • Use grep when you want to find specific text inside files: error messages, function names, configuration values.
  • Use find when you want to locate files by name, extension, size, modification date, or permissions.
  • Use both together for powerful searches: find /project -name "*.py" -exec grep -l "import os" {} \;

Examples

$ grep -rn "TODO" /project/src/          # Find "TODO" inside source files
/project/src/main.py:15:# TODO: refactor
/project/src/utils.py:42:# TODO: add tests

$ find /project -name "*.py" -size +10k   # Find Python files larger than 10KB
/project/src/main.py
/project/tests/test_all.py

3. apt vs apt-get

Summary: Both manage packages on Debian/Ubuntu systems. apt is the newer, more user-friendly command. apt-get is the older, more scriptable command. They use the same package database and repositories.

Featureaptapt-get
Progress barYes (visual)No
Color outputYesNo
Recommended forInteractive terminal useScripts and automation
Stable output formatNo (may change between versions)Yes (reliable for parsing)
Install packagesapt install pkgapt-get install pkg
Remove packagesapt remove pkgapt-get remove pkg
Update package listapt updateapt-get update
Upgrade all packagesapt upgradeapt-get upgrade
Search packagesapt search pkgapt-cache search pkg
Show package infoapt show pkgapt-cache show pkg
List installedapt list --installeddpkg --list
Auto-remove orphansapt autoremoveapt-get autoremove
Full upgradeapt full-upgradeapt-get dist-upgrade

When to Use Each

  • Use apt for day-to-day interactive use. It is easier to type and gives better visual feedback.
  • Use apt-get in shell scripts, cron jobs, and automation. Its output format is stable and predictable.

Examples

$ sudo apt update && sudo apt upgrade    # Interactive: update and upgrade
$ sudo apt install nginx                  # Interactive: install a package
$ apt search "text editor"                # Interactive: search for packages

# In a script:
sudo apt-get update -qq
sudo apt-get install -y nginx            # -y auto-confirms
Note

apt is essentially a nicer front-end that combines features of apt-get and apt-cache. Under the hood, they do the same thing.

4. top vs htop

Summary: Both show real-time system resource usage (CPU, memory, processes). top is pre-installed on every Linux system. htop is a more visual, user-friendly alternative that usually needs to be installed.

Featuretophtop
Pre-installedYes (everywhere)Usually needs installing
ColorsLimitedFull color, visual bars
Mouse supportNoYes
Scroll process listLimitedFull vertical and horizontal scrolling
Kill a processPress k, type PIDSelect with arrows, press F9
Sort by columnPress P (CPU), M (memory)Click column header or press F6
Filter processesPress o (limited)Press F4 (easy filter)
Tree viewPress VPress F5
Per-CPU displayPress 1Always visible as bars
SearchPress LPress F3 or /
CustomizableLimitedPress F2 for setup screen
Show full commandPress cAlways visible (scrollable)

When to Use Each

  • Use top on any system where you cannot install software (minimal servers, containers, recovery environments). It is always available.
  • Use htop on systems where you can install it. It is easier to use, more visual, and more interactive.

Installation

$ sudo apt install htop       # Debian/Ubuntu
$ sudo yum install htop       # CentOS/RHEL
$ sudo pacman -S htop         # Arch

What You See

top shows a text-only display with summary statistics at the top and a process list below. Columns include PID, USER, %CPU, %MEM, COMMAND, and more.

htop shows colored CPU and memory bars at the top, followed by the same process list but with color coding, mouse support, and easier navigation. You can click column headers to sort, click processes to select them, and use function keys for common actions.

5. curl vs wget

Summary: Both download files from the internet. curl is a versatile data transfer tool supporting many protocols. wget specializes in downloading files, especially recursively.

Featurecurlwget
Primary purposeData transfer (flexible)File downloading (focused)
Output defaultPrints to stdoutSaves to file
Save to file-o file or -OAutomatic (or -O file)
Recursive downloadNoYes (-r)
Resume downloads-C --c
Protocols supportedHTTP, HTTPS, FTP, SFTP, SCP, LDAP, SMTP, and many moreHTTP, HTTPS, FTP
POST requests-X POST -d "data"--post-data="data"
Custom headers-H "Header: value"--header="Header: value"
API testingExcellent (widely used)Not typical
JSON support--json '{"key":"val"}'Manual
Follow redirects-L (must specify)Automatic (up to 20)
Mirror websiteNo--mirror
Background downloadNo built-in-b
Download from listNo built-in-i urls.txt

When to Use Each

  • Use curl for API calls, testing endpoints, uploading data, working with REST APIs, or any protocol beyond HTTP/FTP.
  • Use wget for downloading files, mirroring websites, downloading multiple files from a list, or resuming interrupted downloads.

Examples

# Download a file
$ wget https://example.com/file.zip               # Saves to file.zip
$ curl -O https://example.com/file.zip             # -O saves with original name

# Test an API
$ curl -s https://api.example.com/users | jq .     # Pretty-print JSON

# POST JSON data
$ curl -X POST -H "Content-Type: application/json" \
    -d '{"name":"test"}' https://api.example.com/users

# Mirror a website
$ wget --mirror --convert-links https://example.com/

# Download multiple files
$ wget -i list-of-urls.txt

6. Soft Link vs Hard Link

Summary: Both create references to files, but they work fundamentally differently at the filesystem level.

Understanding Inodes
  Filename        Inode       Data Blocks
  --------        -----       -----------
  file.txt  --->  [12345] --> [actual data on disk]
                     ^
  hardlink  --------/         (points to SAME inode)

  softlink  ---> "file.txt"   (points to the FILENAME, not the inode)

Every file on disk has an inode — a data structure that stores the file's metadata and the location of its data blocks. A filename is just a pointer to an inode.

  • A hard link is another filename pointing to the same inode. Both names are equally "real".
  • A soft link (symbolic link / symlink) is a special file that contains a path to another filename. It is like a shortcut.
FeatureHard LinkSoft Link (Symlink)
Points toThe same inode (data)A filename / path
If original is deletedLink still works (data remains)Link breaks (dangling symlink)
Cross filesystemNo (must be same filesystem)Yes
Link to directoryNo (usually not allowed)Yes
Inode numberSame as originalDifferent from original
File size of linkSame as originalSmall (stores path string)
Create commandln file linkln -s file link
IdentifySame inode number (ls -i)l in permissions, -> in ls output

When to Use Each

  • Use soft links in most cases. They are more flexible: they work across filesystems, can point to directories, and are easy to identify.
  • Use hard links when you need a file reference that survives the original being deleted, or for efficient backups (tools like rsnapshot use hard links to save space).

Examples Showing the Difference

$ echo "Hello" > original.txt

# Create both types of links
$ ln original.txt hardlink.txt
$ ln -s original.txt softlink.txt

# Check inodes
$ ls -li
12345 -rw-r--r-- 2 user user 6 Mar 15 10:00 hardlink.txt
12345 -rw-r--r-- 2 user user 6 Mar 15 10:00 original.txt
67890 lrwxrwxrwx 1 user user 12 Mar 15 10:00 softlink.txt -> original.txt

Notice: hardlink.txt and original.txt share inode 12345 (and the link count is 2). The soft link has its own inode (67890) and shows an arrow pointing to the original.

# Now delete the original
$ rm original.txt

$ cat hardlink.txt
Hello              # STILL WORKS - data is still on disk via inode 12345

$ cat softlink.txt
cat: softlink.txt: No such file or directory   # BROKEN - the path it points to no longer exists
Practical Example

Symlinks are commonly used to switch between versions of software: ln -s /opt/python-3.12/bin/python3 /usr/local/bin/python3. When you upgrade, just change where the symlink points.

7. less vs more

Summary: Both are pagers that let you view file contents one screen at a time. less is the improved version of more, and the saying goes: "less is more."

Featurelessmore
Scroll backwardYes (b or arrow keys)No (forward only on most systems)
Scroll forwardYes (f, Space, arrows)Yes (Space)
Search forward/pattern/pattern
Search backward?patternNo
Line numbers-N flagNo
Does not load entire fileCorrect (fast on huge files)Loads entire file
Horizontal scrollingYes (arrow keys)No (wraps lines)
Exit at end of fileNo (stays open)Yes (quits automatically)
Can read from pipeYesYes
Widely availableNearly everywhereEverywhere

When to Use Each

  • Use less almost always. It does everything more does plus backward scrolling, searching, and handles large files efficiently.
  • Use more only in minimal environments where less is not available (rare).

Examples

$ less /var/log/syslog          # Open a file
$ less -N /var/log/syslog       # With line numbers
$ dmesg | less                  # Pipe command output into less
$ less +F /var/log/syslog       # Follow mode (like tail -f, press Ctrl+C to stop following)

8. cat vs less vs head vs tail

Summary: All four display file contents, but each is designed for a different use case.

Featurecatlessheadtail
ShowsEntire file at onceOne screen at a timeFirst N linesLast N lines
ScrollableNo (dumps everything)Yes (forward/backward)NoNo
Good for large filesNo (floods terminal)YesYes (reads only beginning)Yes (reads only end)
Follow modeNoless +FNotail -f
Default linesAllOne screenful1010
Concatenate filesYes (primary purpose)NoNoNo
Show line numbers-n-N-n (means count)-n (means count)
Good for pipingYesYes (as pager)YesYes

When to Use Each

  • cat — small files (under 50 lines), concatenating multiple files, piping to other commands.
  • less — reading any file you want to browse, searching within files, large files.
  • head — quickly checking what is at the beginning of a file (format, headers, first few records).
  • tail — checking the latest entries in log files, monitoring logs in real time with -f.

Examples

$ cat config.txt                  # Small file, view it all
$ cat file1.txt file2.txt > merged.txt  # Concatenate files

$ less /var/log/syslog            # Browse a large log file

$ head -20 data.csv               # Check the first 20 lines (column headers, etc.)
$ head -1 data.csv                # Just see the header row

$ tail -50 /var/log/nginx/error.log       # Last 50 lines of error log
$ tail -f /var/log/nginx/access.log       # Watch log in real time
Wrong: Using cat for Large Files
$ cat /var/log/syslog     # Floods your terminal with thousands of lines
Right: Use the Appropriate Tool
$ less /var/log/syslog    # Browse it at your own pace
$ tail -100 /var/log/syslog   # Just see the latest entries

9. kill vs killall vs pkill

Summary: All three send signals to processes, most commonly to stop them. They differ in how you identify which process to signal.

Featurekillkillallpkill
Identifies process byPID (process ID number)Exact process namePattern matching on name
TargetsOne specific processAll processes with that nameAll matching processes
Requires knowing PIDYesNoNo
Pattern matchingNoNo (exact name only)Yes (regex)
Default signalSIGTERM (15)SIGTERM (15)SIGTERM (15)
Force killkill -9 PIDkillall -9 namepkill -9 pattern
AvailabilityBuilt into every systemMost Linux systemsMost Linux systems
Filter by userNo-u user-u user

When to Use Each

  • kill — when you know the exact PID and want to target one specific process.
  • killall — when you want to stop all instances of a specific program (e.g., all firefox processes).
  • pkill — when you know part of the process name or want to match with a pattern.

Examples

# Using kill (need the PID first)
$ ps aux | grep nginx
root      1234  0.0  0.2  nginx: master process
www-data  1235  0.0  0.3  nginx: worker process
$ kill 1234                    # Send SIGTERM to PID 1234
$ kill -9 1234                 # Force kill if it does not respond

# Using killall (by exact name)
$ killall firefox              # Kill all firefox processes
$ killall -9 python3           # Force kill all python3 processes

# Using pkill (pattern matching)
$ pkill -f "python.*server"    # Kill any process whose full command matches
$ pkill -u user1 python        # Kill python processes owned by user1
Caution

killall and pkill can affect multiple processes at once. Always check what matches first with pgrep (which uses the same matching as pkill but only shows PIDs):

$ pgrep -a python             # Show PIDs and command lines that match
1234 python3 server.py
5678 python3 worker.py

10. scp vs rsync

Summary: Both copy files between machines over SSH. rsync is the more powerful and efficient option in almost every scenario.

Featurescprsync
Transfer methodFull copy every timeIncremental (only changed bytes)
Resume interrupted transferNo (starts over)Yes (--partial)
CompressionYes (-C)Yes (-z)
Preserve permissionsYes (-p)Yes (-a or -p)
Preserve timestampsYes (-p)Yes (-a or -t)
Delete extra files at destNoYes (--delete)
Exclude filesNoYes (--exclude)
Dry runNoYes (--dry-run)
Show progressDefault--progress or -P
Bandwidth limit-l (some versions)--bwlimit=KBPS
Copy symlinksFollows by defaultConfigurable (-l, -L)
SimplicitySimpler syntaxMore flags but more power
Speed (repeated transfers)Slow (copies everything again)Fast (only copies changes)

When to Use Each

  • Use scp for quick, one-time file copies when simplicity matters and you do not need any advanced features.
  • Use rsync for everything else: regular syncs, large transfers, backups, transfers that might be interrupted, or when you need to exclude files.

Examples

# scp: simple file copy
$ scp file.txt user@server:/home/user/
$ scp -r /project user@server:/backup/

# rsync: smarter copy
$ rsync -avz /project/ user@server:/backup/project/
$ rsync -avz --exclude='.git' --exclude='node_modules' /project/ user@server:/deploy/
$ rsync -avz --dry-run /data/ user@server:/data/    # Preview first
$ rsync -avz --delete /project/ user@server:/mirror/  # Mirror exactly
Practical Advice

If you are copying a single small file once, scp is fine. For anything more involved — large directories, repeated syncs, backups, or when you want a dry run — use rsync. Many system administrators use rsync exclusively.

Exercises

Exercise 1: Choose the Right Command

For each scenario, choose the best command and explain why:

  1. You want to find all files in /var/log modified in the last 24 hours.
  2. You want to find all lines containing "ERROR" in /var/log/syslog.
  3. You want to keep a remote server's project directory in sync with your local copy.
Show Solution
  1. find /var/log -mtime 0 — find searches by file attributes, and -mtime 0 means modified within the last 24 hours.
  2. grep "ERROR" /var/log/syslog — grep searches inside file contents.
  3. rsync -avz /project/ user@server:/project/ — rsync only transfers changed files, making it efficient for repeated syncing.
Exercise 2: Link Behavior

Create a file called data.txt, make a hard link and a soft link to it, then delete the original. What happens to each link? Verify by reading both links.

Show Solution 
$ echo "test data" > data.txt
$ ln data.txt hard.txt
$ ln -s data.txt soft.txt
$ rm data.txt
$ cat hard.txt
test data         # Works! Hard link still has the data.
$ cat soft.txt
cat: soft.txt: No such file or directory   # Broken! Points to deleted name.
Quick Quiz: Which command is better for API testing — curl or wget?
curl is better for API testing. It outputs to stdout by default, supports many protocols, handles POST/PUT/DELETE requests naturally, and is the industry standard for testing REST APIs.
