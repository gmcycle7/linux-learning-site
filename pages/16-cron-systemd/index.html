Chapter 16: Cron Jobs & Systemd

Running commands manually is fine for one-off tasks, but real-world Linux systems depend on automation. Backups need to happen every night, log files need rotating, services need to start at boot, and health checks need to run around the clock — all without a human typing commands. This chapter teaches you the two pillars of Linux automation: cron (the classic task scheduler) and systemd (the modern service and system manager).

1. What is Task Scheduling?

Mental Model: Task Scheduling

Think of task scheduling like setting alarms on your phone. You set the alarm once (define the schedule and the action), and the phone wakes you up at the right time every day — you don't need to remember to do it yourself.

On Linux, the cron daemon is like a tireless alarm clock that checks every minute: “Is there a job scheduled right now?” If yes, it runs the command. Systemd timers are a more modern alternative that work the same way but are integrated into the systemd service manager.

Common tasks you would schedule:

  • Backups — Archive important files nightly to a remote server.
  • Log cleanup — Delete or compress old log files to free disk space.
  • Monitoring — Check disk usage every hour and send an alert if it exceeds 90%.
  • Updates — Pull the latest data from an API every 15 minutes.
  • Reports — Generate and email a daily summary report.
  • Certificate renewal — Renew SSL/TLS certificates before they expire.

2. Cron — The Classic Scheduler

Cron is a time-based job scheduler that has been part of Unix and Linux since the 1970s. The word comes from Chronos, the Greek word for time. It consists of:

  • The cron daemon (crond or cron) — A background process that runs continuously and checks the schedule every minute.
  • Crontab files — Configuration files where users define their scheduled jobs.
  • System cron directories — Special folders for system-wide scheduled scripts.

The daemon starts at boot and sleeps between checks. Every minute, it wakes up, reads all crontab files, and executes any jobs whose schedule matches the current time.

The Cron Schedule Format

Every cron job line follows this format:

 ┌───────────── Minute (0 - 59)
 │ ┌───────────── Hour (0 - 23)
 │ │ ┌───────────── Day of month (1 - 31)
 │ │ │ ┌───────────── Month (1 - 12)
 │ │ │ │ ┌───────────── Day of week (0 - 7, Sun = 0 or 7)
 │ │ │ │ │
 * * * * *  command_to_execute

Each field can contain:

  • * — Any value (wildcard).
  • 5 — A specific value.
  • 1,3,5 — A list of values.
  • 1-5 — A range of values.
  • */10 — A step value (every 10th).

Common Schedule Patterns

ScheduleCron ExpressionMeaning
Every minute* * * * *Runs at the start of every minute
Every 5 minutes*/5 * * * *Runs at :00, :05, :10, :15, ...
Every 15 minutes*/15 * * * *Runs at :00, :15, :30, :45

Shortcut Strings

Many cron implementations support shortcuts instead of the five-field format:

  • @reboot — Run once at startup
  • @yearly or @annually — 0 0 1 1 *
  • @monthly — 0 0 1 * *
  • @weekly — 0 0 * * 0
  • @daily or @midnight — 0 0 * * *
  • @hourly — 0 * * * *

3. Managing Cron Jobs with crontab

The crontab command is how you create, view, and manage your personal cron jobs. Each user has their own crontab file.

Essential crontab Commands

CommandDescription
crontab -eEdit your crontab (opens in your default editor)
crontab -lList (display) your current crontab
crontab -rRemove (delete) your entire crontab
crontab -u username -eEdit another user's crontab (requires root)
crontab -u username -lList another user's crontab (requires root)
Warning: crontab -r Deletes Everything

crontab -r removes your entire crontab without asking for confirmation. There is no undo. Always back up your crontab first with crontab -l > my_crontab_backup.txt before making risky changes. On some keyboards, r is right next to e — one slip and your jobs are gone.

Crontab Examples

# View your current cron jobs
$ crontab -l
no crontab for user

# Edit your crontab (opens in vi/nano)
$ crontab -e

Inside the crontab file, you would add lines like these:

# Back up the home directory every day at 2 AM
0 2 * * * tar -czf /backup/home_$(date +\%Y\%m\%d).tar.gz /home/user

# Delete log files older than 30 days every Sunday at 3 AM
0 3 * * 0 find /var/log/myapp -name "*.log" -mtime +30 -delete

# Check disk usage every hour, email alert if above 90%
0 * * * * df -h / | awk 'NR==2 {if ($5+0 > 90) print "Disk alert: "$5}' | mail -s "Disk Warning" admin@example.com

# Pull latest data from API every 15 minutes
*/15 * * * * /usr/local/bin/fetch_data.sh >> /var/log/fetch.log 2>&1

# Restart a service every Monday at 4 AM
0 4 * * 1 /usr/bin/systemctl restart myapp.service

# Run a database cleanup every night at midnight
0 0 * * * /usr/local/bin/db_cleanup.py >> /var/log/db_cleanup.log 2>&1

# Sync files to remote server twice a day
0 6,18 * * * rsync -avz /data/ user@backup-server:/data/ >> /var/log/sync.log 2>&1

# Generate a weekly report every Friday at 5 PM
0 17 * * 5 /usr/local/bin/weekly_report.sh | mail -s "Weekly Report" team@example.com

# Renew SSL certificates on the 1st of every month
0 3 1 * * /usr/bin/certbot renew --quiet >> /var/log/certbot.log 2>&1

# Clear tmp directory every day at 4 AM
0 4 * * * find /tmp -type f -atime +7 -delete

# Monitor website uptime every 5 minutes
*/5 * * * * curl -sf https://example.com > /dev/null || echo "Site down!" | mail -s "Alert" admin@example.com

# Run a script at boot (use @reboot)
@reboot /usr/local/bin/start_my_service.sh

Cron Environment Gotchas

Warning: Cron Has a Minimal Environment

Cron jobs do not run in your normal shell environment. The PATH is usually just /usr/bin:/bin, and environment variables from your .bashrc or .profile are not loaded. This is the number-one cause of “it works in my terminal but not in cron.”

Solutions for PATH issues:

# Solution 1: Use absolute paths for every command
0 2 * * * /usr/bin/python3 /home/user/scripts/backup.py

# Solution 2: Set PATH at the top of your crontab
PATH=/usr/local/bin:/usr/bin:/bin:/usr/local/sbin:/usr/sbin
0 2 * * * python3 /home/user/scripts/backup.py

# Solution 3: Source your profile inside the job
0 2 * * * . /home/user/.profile && python3 /home/user/scripts/backup.py

# Solution 4: Set variables directly in the crontab
SHELL=/bin/bash
MAILTO=admin@example.com
HOME=/home/user

Other common gotchas:

  • Percent signs (%) — In crontab, % is a special character (newline). Escape it as \%. This is why the date command above uses \%Y\%m\%d instead of %Y%m%d.
  • No terminal — Cron jobs have no terminal attached. Interactive commands will fail.
  • Output goes nowhere — By default, cron mails output to the user. If mail is not configured, output is lost. Always redirect: >> /var/log/myjob.log 2>&1
  • Working directory — Cron starts in the user's home directory. Use cd or absolute paths to be safe.

Debugging Cron Jobs

# Check if cron daemon is running
$ systemctl status cron
● cron.service - Regular background program processing daemon
     Active: active (running) since Mon 2024-01-15 08:00:00 UTC

# View cron logs (Debian/Ubuntu)
$ grep CRON /var/log/syslog

# View cron logs (RHEL/CentOS)
$ grep CRON /var/log/cron

# Test your cron command manually first
$ /bin/bash -c 'your_cron_command_here'

4. System Cron Directories

In addition to user crontabs, Linux provides system-wide cron directories for scripts that need to run as root:

DirectoryRunsUse Case
/etc/cron.hourly/Once per hourFrequent checks (monitoring, log rotation)
/etc/cron.daily/Once per dayBackups, cleanup, updates
/etc/cron.weekly/Once per weekWeekly reports, database maintenance
/etc/cron.monthly/Once per monthCertificate renewal, monthly reports
/etc/cron.d/Custom schedulePackage-installed cron jobs with full cron syntax

How to use them: Drop an executable script into the appropriate directory. No cron expression needed (except for /etc/cron.d/).

# Create a daily cleanup script
$ sudo nano /etc/cron.daily/cleanup-tmp
# Add your script content, then make it executable:
$ sudo chmod +x /etc/cron.daily/cleanup-tmp

# Verify it is listed
$ ls -la /etc/cron.daily/
-rwxr-xr-x 1 root root  123 Jan 15 10:00 cleanup-tmp
-rwxr-xr-x 1 root root  379 Jan  5 08:00 logrotate
-rwxr-xr-x 1 root root  249 Jan  5 08:00 apt-compat
When to Use Each Approach
  • User crontab (crontab -e) — For personal tasks that run as your user.
  • /etc/cron.d/ — For system tasks that need a custom schedule (full cron syntax, includes a username field).
  • /etc/cron.daily/ etc. — For simple scripts that just need to run at a regular interval. No schedule to configure.

Files in /etc/cron.d/ have a slightly different format — they include a username field:

# Format for /etc/cron.d/ files (note the username field)
*/10 * * * * root /usr/local/bin/health_check.sh
0 2 * * * www-data /var/www/scripts/cleanup.sh

5. Systemd Basics

Mental Model: Systemd

If cron is the alarm clock, systemd is the entire building management system. It does not just schedule tasks — it manages everything that runs on a modern Linux system: services (web servers, databases), mount points, network configuration, logging, and yes, even scheduled tasks (timers).

Systemd is the first process that runs (PID 1). It starts all other services in the correct order, monitors them, and restarts them if they crash. Think of it as the orchestra conductor that makes sure every instrument starts on cue.

Systemd replaced the older SysVinit (and Upstart) on most major Linux distributions. Here is why:

FeatureSysVinit (Old)Systemd (Modern)
Boot speedSequential (slow)Parallel (fast)
Service filesShell scripts in /etc/init.d/Declarative unit files
Dependency handlingManual orderingAutomatic dependency resolution
Service monitoringBasic PID filesFull process tracking via cgroups
LoggingText files (syslog)Structured journal (journald)
Restart on crashRequires extra toolsBuilt-in (Restart= directive)
Socket activationNot supportedBuilt-in

Unit Files

Systemd manages things through unit files. The most common types are:

  • .service — A daemon or one-shot process (web server, database, backup script).
  • .timer — A scheduled trigger (replaces cron jobs).
  • .socket — A network or IPC socket for socket activation.
  • .mount — A filesystem mount point.
  • .target — A group of units (similar to runlevels).

Unit files live in these directories (in order of priority):

DirectoryPurpose
/etc/systemd/system/Local admin customizations (highest priority)
/run/systemd/system/Runtime units (generated on the fly)
/usr/lib/systemd/system/Units installed by packages (do not edit directly)

systemctl is the primary command for interacting with systemd. It lets you start, stop, restart, enable, and inspect services.

Essential systemctl Commands

8. Creating a Custom Systemd Service

Let's walk through creating a simple service from scratch. Suppose you have a Python web application at /opt/myapp/app.py and you want systemd to manage it.

Step 1: Create the Service File

$ sudo nano /etc/systemd/system/myapp.service

Add the following content:

[Unit]
Description=My Python Web Application
Documentation=https://github.com/myuser/myapp
After=network.target
Wants=network.target

[Service]
Type=simple
User=www-data
Group=www-data
WorkingDirectory=/opt/myapp
ExecStart=/usr/bin/python3 /opt/myapp/app.py
Restart=on-failure
RestartSec=5
StandardOutput=journal
StandardError=journal
Environment=NODE_ENV=production
Environment=PORT=8080

[Install]
WantedBy=multi-user.target

Understanding Each Section

SectionDirectiveMeaning
[Unit]DescriptionHuman-readable name shown in systemctl status
AfterStart this service only after the network is up
WantsWeak dependency — try to start network, but don't fail if it doesn't
[Service]Type=simpleThe process started by ExecStart is the main process
User / GroupRun the service as this user (not root)
WorkingDirectorySet the working directory before starting
ExecStartThe command to run
Restart=on-failureAutomatically restart if the process crashes
RestartSec=5Wait 5 seconds before restarting
EnvironmentSet environment variables for the process
[Install]WantedByWhich target pulls in this service (multi-user = normal boot)

Step 2: Reload, Enable, and Start

# Tell systemd about the new file
$ sudo systemctl daemon-reload

# Enable the service to start at boot
$ sudo systemctl enable myapp.service
Created symlink /etc/systemd/system/multi-user.target.wants/myapp.service
  → /etc/systemd/system/myapp.service.

# Start the service now
$ sudo systemctl start myapp.service

Step 3: Verify It Works

$ systemctl status myapp.service
● myapp.service - My Python Web Application
     Loaded: loaded (/etc/systemd/system/myapp.service; enabled)
     Active: active (running) since Mon 2024-01-15 14:30:00 UTC; 10s ago
       Docs: https://github.com/myuser/myapp
   Main PID: 6789 (python3)
      Tasks: 3 (limit: 4915)
     Memory: 24.5M
        CPU: 150ms
     CGroup: /system.slice/myapp.service
             └─6789 /usr/bin/python3 /opt/myapp/app.py

Jan 15 14:30:00 server systemd[1]: Started My Python Web Application.
Jan 15 14:30:01 server python3[6789]: Server running on port 8080

# View the logs
$ journalctl -u myapp.service -f

Step 4: Managing Your Service

# Stop the service
$ sudo systemctl stop myapp.service

# Restart after code changes
$ sudo systemctl restart myapp.service

# If you edit the .service file, always reload first
$ sudo systemctl daemon-reload
$ sudo systemctl restart myapp.service
Warning: Always Run daemon-reload After Editing Unit Files

If you modify a .service file and try to restart without running sudo systemctl daemon-reload first, systemd will use the old cached version. You will see a warning: “Warning: The unit file, source configuration file or drop-ins of myapp.service changed on disk. Run 'systemctl daemon-reload' to reload units.”

9. Systemd Timers vs Cron

Systemd timers are the modern alternative to cron jobs. They consist of two unit files: a .timer file (the schedule) and a matching .service file (the task to run).

Example: A Systemd Timer

Create a timer that runs a backup script daily at 2 AM:

# /etc/systemd/system/backup.service
[Unit]
Description=Daily backup job

[Service]
Type=oneshot
ExecStart=/usr/local/bin/backup.sh
# /etc/systemd/system/backup.timer
[Unit]
Description=Run backup daily at 2 AM

[Timer]
OnCalendar=*-*-* 02:00:00
Persistent=true

[Install]
WantedBy=timers.target
# Enable and start the timer (not the service)
$ sudo systemctl daemon-reload
$ sudo systemctl enable --now backup.timer

# Check timer status
$ systemctl list-timers
NEXT                        LEFT       LAST                        PASSED  UNIT          ACTIVATES
Tue 2024-01-16 02:00:00 UTC 11h left   Mon 2024-01-15 02:00:00 UTC 12h ago backup.timer  backup.service
...

Comparison Table

FeatureCronSystemd Timers
Setup complexitySimple — one line per jobMore complex — two unit files needed
LoggingManual (redirect output)Automatic via journal
Missed jobsSkipped if system was offPersistent=true catches up missed runs
DependenciesNoneCan depend on other services or targets
Resource controlNoneCan limit CPU, memory, IO via cgroups
Randomized delayNot built-inRandomizedDelaySec= to spread load
AccuracyMinute-level onlySecond-level or monotonic (every N seconds)
Viewing schedulecrontab -lsystemctl list-timers
Viewing logsGrep syslog or custom logjournalctl -u <service>
User familiarityUniversally knownNewer, less familiar
Available onAll Unix/Linux systemsSystemd-based distros only
EnvironmentMinimal PATH, no shell profileControlled via unit file directives
Which Should You Use?
  • Use cron for quick, simple scheduled tasks. It is easier to set up and universally understood.
  • Use systemd timers when you need logging integration, dependency management, resource limits, catch-up after downtime (Persistent=true), or second-level precision.
  • For most beginner use cases, cron is perfectly fine. As your needs grow, systemd timers are worth learning.

Quick Quizzes

Quiz 1: What does the cron expression 30 4 * * 0 mean?
It runs at 4:30 AM every Sunday. Reading the fields: minute = 30, hour = 4, day of month = any, month = any, day of week = 0 (Sunday).
Quiz 2: You edited /etc/systemd/system/myapp.service and then ran sudo systemctl restart myapp. The service restarted, but your changes do not seem to have taken effect. What did you forget?
You forgot to run sudo systemctl daemon-reload before restarting. Systemd caches unit file contents in memory. Without daemon-reload, it still uses the old version of the file. The correct sequence is: edit the file, then daemon-reload, then restart.
