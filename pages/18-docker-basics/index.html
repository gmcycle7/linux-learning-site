Chapter 18: Docker Basics

Docker has revolutionized how software is built, shipped, and run. Instead of wrestling with "it works on my machine" problems, Docker lets you package an application along with everything it needs into a portable, self-contained unit called a container. If you can run Docker, you can run the container — on any Linux distribution, any cloud provider, any machine.

This chapter teaches you the essential Docker commands and concepts you need as a Linux user, from running your first container to building custom images and orchestrating multi-service applications.

1. What Is Docker?

Mental Model: The Shipping Container Analogy

Before standardized shipping containers, goods were loaded loose onto ships — fragile items broke, perishables spoiled, and every port needed different equipment. Then came the intermodal shipping container: a standard steel box. No matter what was inside (electronics, food, furniture), the container was handled the same way by cranes, trucks, and ships worldwide.

Docker does the same thing for software. A Docker container is a standardized unit that packages your application, its libraries, its configuration, and its dependencies into one portable box. The "crane" is the Docker engine — it runs containers identically on your laptop, your test server, or a cloud VM.

Docker is a platform for developing, shipping, and running applications inside containers. A container is a lightweight, standalone, executable package that includes everything needed to run a piece of software: the code, runtime, system tools, libraries, and settings.

Containers vs Virtual Machines

Containers are often compared to virtual machines (VMs), but they work very differently under the hood:

FeatureContainersVirtual Machines
Virtualization levelOS-level (shares host kernel)Hardware-level (full guest OS)
Startup timeSecondsMinutes
SizeMegabytes (typically 10–500 MB)Gigabytes (typically 1–20 GB)
Resource overheadMinimal (no duplicate OS)Heavy (full OS per VM)
IsolationProcess-level isolation via namespacesFull hardware-level isolation
PerformanceNear-nativeSome overhead from hypervisor
PortabilityRuns anywhere Docker is installedRequires compatible hypervisor
Use caseMicroservices, CI/CD, dev environmentsRunning different OS, strict isolation
Mental Model: Apartments vs Houses

Think of virtual machines as separate houses on a street. Each house has its own foundation, plumbing, electrical, roof — completely independent but expensive to build and maintain.

Containers are like apartments in a building. They share the foundation, plumbing, and structure (the host kernel), but each apartment has its own interior, locks, and furnishings (its own filesystem, processes, and network). Much cheaper and faster to set up, but they share the building infrastructure.

Why Docker Matters

  • Consistency — "It works on my machine" becomes "it works everywhere."
  • Speed — Containers start in seconds, not minutes.
  • Isolation — Each container has its own filesystem and process tree.
  • Efficiency — Run dozens of containers on a single machine.
  • Reproducibility — A Dockerfile is an exact recipe for building an environment.
  • CI/CD friendly — Build, test, and deploy in identical environments.

2. Installing Docker

On Ubuntu/Debian, install Docker Engine from the official Docker repository for the latest version:

# Update package index and install prerequisites
$ sudo apt update
$ sudo apt install -y ca-certificates curl gnupg

# Add Docker's official GPG key
$ sudo install -m 0755 -d /etc/apt/keyrings
$ curl -fsSL https://download.docker.com/linux/ubuntu/gpg | sudo gpg --dearmor -o /etc/apt/keyrings/docker.gpg

# Set up the Docker repository
$ echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.gpg] \
  https://download.docker.com/linux/ubuntu $(lsb_release -cs) stable" | \
  sudo tee /etc/apt/sources.list.d/docker.list > /dev/null

# Install Docker Engine
$ sudo apt update
$ sudo apt install -y docker-ce docker-ce-cli containerd.io docker-compose-plugin
# Verify the installation
$ docker --version
Docker version 24.0.7, build afdd53b

# Add your user to the docker group (avoids needing sudo every time)
$ sudo usermod -aG docker $USER

# Log out and back in, then verify
$ docker info

 ...
Server: Docker Engine - Community

  Version:          24.0.7
  ...

3. Key Concepts

Before diving into commands, understand these core terms:

  • Image — A read-only template with instructions for creating a container. Think of it as a blueprint or a snapshot. Images are built in layers.
  • Container — A running instance of an image. You can create many containers from one image, each isolated from the others.
  • Registry — A storage and distribution system for images. Docker Hub (hub.docker.com) is the default public registry.
  • Dockerfile — A text file containing step-by-step instructions to build an image.
  • Layer — Each instruction in a Dockerfile creates a layer. Layers are cached and reused, making builds fast.
  • Volume — Persistent storage that survives container restarts and removal.
  • Tag — A version label for an image, such as nginx:1.25 or ubuntu:22.04.
Mental Model: Image → Container Relationship
  +---------------------+
  |      Dockerfile      |   ← Recipe (instructions)
  +---------------------+
            |
        docker build
            |
            v
  +---------------------+
  |       Image          |   ← Blueprint (read-only template)
  |  (e.g., nginx:1.25) |
  +---------------------+
        /       \
   docker run  docker run
      /             \
     v               v
+-----------+   +-----------+
| Container |   | Container |   ← Running instances
|   (web1)  |   |   (web2)  |      (isolated, writable)
+-----------+   +-----------+

One image can spawn many containers. Each container gets its own writable layer on top of the read-only image layers. Deleting a container does not affect the image or other containers.

4. docker run — Running Containers

The docker run command creates and starts a container from an image. It is the most important Docker command you will use.

# Basic syntax
$ docker run [OPTIONS] IMAGE [COMMAND] [ARGS]

Key Options

OptionPurposeExample
-dDetached mode (run in background)docker run -d nginx
-itInteractive + terminal (for shell access)docker run -it ubuntu bash
--nameAssign a name to the containerdocker run --name web nginx
-pMap host port to container portdocker run -p 8080:80 nginx
-vMount a volume or bind mountdocker run -v /data:/app/data nginx
--rmRemove container when it stopsdocker run --rm nginx
-eSet environment variabledocker run -e DB_HOST=db nginx
--networkConnect to a specific networkdocker run --network mynet nginx

Examples

# Run an interactive Ubuntu container with a bash shell
$ docker run -it ubuntu bash
root@a1b2c3d4e5f6:/# ls
bin  boot  dev  etc  home  lib  ...
root@a1b2c3d4e5f6:/# exit
# Run Nginx in the background on port 8080
$ docker run -d --name my-web -p 8080:80 nginx
f7a8b9c0d1e2f3a4b5c6d7e8f9a0b1c2d3e4f5a6b7c8d9e0f1a2b3c4d5e6f7a8
# Run a container with environment variables
$ docker run -d --name mydb \
  -e MYSQL_ROOT_PASSWORD=secret \
  -e MYSQL_DATABASE=myapp \
  -p 3306:3306 \
  mysql:8.0
# Run a one-off command and auto-remove the container
$ docker run --rm alpine echo "Hello from Alpine!"
Hello from Alpine!
# Mount a host directory into the container
$ docker run -d --name web \
  -p 8080:80 \
  -v /home/user/website:/usr/share/nginx/html:ro \
  nginx
# Run a container on a specific network
$ docker run -d --name api --network my-network node:18-alpine
# Run a Python script inside a container
$ docker run --rm -v $(pwd):/app -w /app python:3.11 python script.py
# Run a Redis cache in the background
$ docker run -d --name cache -p 6379:6379 redis:7-alpine
# Run with resource limits
$ docker run -d --name limited --memory=512m --cpus=1.5 nginx
# Run with a restart policy (auto-restart on failure)
$ docker run -d --name resilient --restart unless-stopped nginx
# Run with multiple port mappings
$ docker run -d --name multi-port -p 8080:80 -p 8443:443 nginx
# Run with an env file instead of individual -e flags
$ docker run -d --name app --env-file .env myapp:latest
Caution: When using -p 8080:80, the format is HOST_PORT:CONTAINER_PORT. A common mistake is reversing the order. The host port comes first.

Security Warning: Untrusted Images

Never blindly pull and run images from unknown sources. Docker images can contain malicious software, cryptocurrency miners, or backdoors. Always:

  • Prefer official images (marked with a blue badge on Docker Hub).
  • Check the Dockerfile source if available.
  • Verify the publisher and download count.
  • Scan images for vulnerabilities: docker scout cves IMAGE.

6. docker ps — Listing Containers

Use docker ps to see what containers are running (or have run).

# List running containers
$ docker ps
CONTAINER ID   IMAGE   COMMAND                  CREATED          STATUS          PORTS                  NAMES
f7a8b9c0d1e2   nginx   "/docker-entrypoint.…"   10 minutes ago   Up 10 minutes   0.0.0.0:8080->80/tcp   my-web
# List ALL containers (including stopped)
$ docker ps -a
CONTAINER ID   IMAGE    COMMAND     CREATED          STATUS                      NAMES
f7a8b9c0d1e2   nginx    "..."       10 min ago       Up 10 minutes               my-web
a1b2c3d4e5f6   ubuntu   "bash"      30 min ago       Exited (0) 25 min ago       keen_tesla
# Show only container IDs (useful for scripting)
$ docker ps -q
f7a8b9c0d1e2
# Show all container IDs (running + stopped)
$ docker ps -aq
# Filter by status
$ docker ps --filter "status=exited"
# Filter by name
$ docker ps --filter "name=web"
# Filter by image
$ docker ps --filter "ancestor=nginx"
# Custom output format
$ docker ps --format "table {{.Names}}\t{{.Image}}\t{{.Status}}\t{{.Ports}}"
NAMES    IMAGE   STATUS          PORTS
my-web   nginx   Up 10 minutes   0.0.0.0:8080->80/tcp

7. docker stop / start / restart

Manage the lifecycle of running containers.

# Stop a running container (sends SIGTERM, then SIGKILL after 10s)
$ docker stop my-web
my-web
# Start a stopped container
$ docker start my-web
my-web
# Restart a container (stop + start)
$ docker restart my-web
# Stop with a custom timeout (wait 30 seconds before SIGKILL)
$ docker stop -t 30 my-web
# Stop ALL running containers
$ docker stop $(docker ps -q)
# Force kill a container (immediate SIGKILL, no graceful shutdown)
$ docker kill my-web
Tip

Always prefer docker stop over docker kill. Stopping sends SIGTERM first, giving the application time to clean up (close database connections, flush buffers, etc.). Killing sends SIGKILL immediately, which can cause data loss.

8. docker rm — Removing Containers

Stopped containers still consume disk space. Remove them to reclaim resources.

# Remove a stopped container
$ docker rm my-web
# Force-remove a running container (stops it first)
$ docker rm -f my-web
# Remove multiple containers
$ docker rm container1 container2 container3
# Remove ALL stopped containers
$ docker container prune
WARNING! This will remove all stopped containers.
Are you sure you want to continue? [y/N] y
Deleted Containers:
a1b2c3d4e5f6...
Total reclaimed space: 150MB
# Remove all stopped containers (scripting approach)
$ docker rm $(docker ps -aq --filter "status=exited")
Tip

Use --rm with docker run to automatically remove the container when it exits. This is ideal for one-off commands and testing.

9. docker exec — Running Commands in Containers

Use docker exec to run commands inside an already running container. This is essential for debugging and maintenance.

# Open an interactive shell in a running container
$ docker exec -it my-web bash
root@f7a8b9c0d1e2:/# ls /usr/share/nginx/html
50x.html  index.html
# Run a single command without entering the container
$ docker exec my-web cat /etc/nginx/nginx.conf
# Check which processes are running inside the container
$ docker exec my-web ps aux
USER       PID  %CPU %MEM  COMMAND
root         1   0.0  0.1  nginx: master process
nginx       29   0.0  0.0  nginx: worker process
# If bash is not available, try sh (common in Alpine-based images)
$ docker exec -it my-alpine-container sh
# Run a command as a specific user
$ docker exec -u www-data my-web whoami
www-data
# Set environment variables for the exec session
$ docker exec -e MY_VAR=hello my-web env | grep MY_VAR
MY_VAR=hello
Common Mistake: docker exec only works on running containers. If the container is stopped, start it first with docker start, then exec into it.

10. docker logs — Viewing Container Logs

Containers write output to stdout and stderr, and Docker captures it all.

# View all logs from a container
$ docker logs my-web
# Follow logs in real time (like tail -f)
$ docker logs -f my-web
172.17.0.1 - - [15/Jan/2025:10:30:01 +0000] "GET / HTTP/1.1" 200 615
172.17.0.1 - - [15/Jan/2025:10:30:05 +0000] "GET /favicon.ico HTTP/1.1" 404 153
^C
# Show only the last 20 lines
$ docker logs --tail 20 my-web
# Show logs with timestamps
$ docker logs -t my-web
2025-01-15T10:30:01.123456789Z 172.17.0.1 - - "GET / HTTP/1.1" 200
# Show logs since a specific time
$ docker logs --since 2h my-web
# Or with a timestamp:
$ docker logs --since "2025-01-15T10:00:00" my-web

11. Dockerfile — Building Custom Images

A Dockerfile is a plain text file containing instructions that tell Docker how to build an image. Each instruction creates a new layer in the image.

Key Dockerfile Instructions

InstructionPurposeExample
FROMBase image to start fromFROM ubuntu:22.04
RUNExecute a command during buildRUN apt update && apt install -y curl
COPYCopy files from host to imageCOPY ./app /app
ADDLike COPY, but also handles URLs and tar extractionADD archive.tar.gz /app
WORKDIRSet the working directoryWORKDIR /app
EXPOSEDocument which port the container listens onEXPOSE 8080
ENVSet environment variablesENV NODE_ENV=production
CMDDefault command when container startsCMD ["node", "server.js"]
ENTRYPOINTMain executable (harder to override than CMD)ENTRYPOINT ["python"]
ARGBuild-time variablesARG VERSION=1.0
CMD vs ENTRYPOINT

CMD provides default arguments that can be overridden at run time. ENTRYPOINT defines the main executable. When both are used, CMD provides default arguments to ENTRYPOINT. Use ENTRYPOINT when the container should always run a specific program. Use CMD when you want flexibility.

Example: Simple Web Server

# Dockerfile for a simple Node.js web server

# Start from the official Node.js Alpine image (small footprint)
FROM node:18-alpine

# Set the working directory inside the container
WORKDIR /app

# Copy package files first (better layer caching)
COPY package*.json ./

# Install dependencies
RUN npm install --production

# Copy application source code
COPY . .

# Document the port the app uses
EXPOSE 3000

# Set a runtime environment variable
ENV NODE_ENV=production

# Command to run when the container starts
CMD ["node", "server.js"]

Example: Python Flask Application

# Dockerfile for a Python Flask app
FROM python:3.11-slim

WORKDIR /app

# Copy and install dependencies first (caching)
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

# Copy the rest of the application
COPY . .

EXPOSE 5000

CMD ["python", "app.py"]

Example: Static Website with Nginx

# Dockerfile for a static website
FROM nginx:alpine

# Remove default Nginx content
RUN rm -rf /usr/share/nginx/html/*

# Copy our static files
COPY ./html /usr/share/nginx/html

EXPOSE 80

CMD ["nginx", "-g", "daemon off;"]

Example: Multi-Stage Build (smaller final image)

# Stage 1: Build
FROM node:18-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm install
COPY . .
RUN npm run build

# Stage 2: Production (only the built output)
FROM nginx:alpine
COPY --from=builder /app/dist /usr/share/nginx/html
EXPOSE 80
CMD ["nginx", "-g", "daemon off;"]

Example: Using ENTRYPOINT with CMD

# Container always runs Python, CMD provides default script
FROM python:3.11-slim
WORKDIR /app
COPY . .
ENTRYPOINT ["python"]
CMD ["main.py"]

# docker run myimage          → runs "python main.py"
# docker run myimage test.py  → runs "python test.py"

Example: Using ARG for Build-Time Variables

FROM ubuntu:22.04
ARG APP_VERSION=1.0
ENV APP_VERSION=${APP_VERSION}
RUN echo "Building version ${APP_VERSION}"
COPY . /app
CMD ["/app/start.sh"]

# Build with a custom version:
# docker build --build-arg APP_VERSION=2.0 -t myapp:2.0 .

Example: .dockerignore File

# .dockerignore — keep your image lean
node_modules
.git
.gitignore
README.md
Dockerfile
.dockerignore
*.log
.env
Best Practice: Layer Caching

Docker caches each layer. If a layer has not changed, Docker reuses the cache. This is why you should copy dependency files first (like package.json or requirements.txt) and install dependencies before copying the rest of the source code. That way, dependencies are only reinstalled when the dependency file changes, not every time you change a line of code.

12. docker build — Building Images

Use docker build to turn a Dockerfile into an image.

# Build an image from the current directory (. is the build context)
$ docker build -t myapp:1.0 .
[+] Building 15.2s (10/10) FINISHED
 => [1/5] FROM node:18-alpine
 => [2/5] WORKDIR /app
 => [3/5] COPY package*.json ./
 => [4/5] RUN npm install --production
 => [5/5] COPY . .
 => exporting to image
 => naming to docker.io/library/myapp:1.0
# Build with a specific Dockerfile name
$ docker build -t myapp:1.0 -f Dockerfile.prod .
# Build without using cache (force fresh build)
$ docker build --no-cache -t myapp:1.0 .
# Build with build arguments
$ docker build --build-arg APP_VERSION=2.0 -t myapp:2.0 .
# Build and see full output (not collapsed)
$ docker build --progress=plain -t myapp:1.0 .
Common Mistake: Forgetting the . (dot) at the end of docker build. The dot tells Docker to use the current directory as the build context. Without it, the command will fail.

13. Docker Compose — Multi-Service Applications

Docker Compose lets you define and manage multi-container applications using a single YAML file. Instead of running multiple docker run commands with long option lists, you describe your entire stack in a docker-compose.yml file and bring it up with one command.

Basic Structure

# docker-compose.yml
version: "3.8"

services:
  web:
    image: nginx:alpine
    ports:
      - "8080:80"
    volumes:
      - ./html:/usr/share/nginx/html
    depends_on:
      - api

  api:
    build: ./api
    ports:
      - "3000:3000"
    environment:
      - DB_HOST=db
      - DB_PORT=5432
    depends_on:
      - db

  db:
    image: postgres:15-alpine
    environment:
      - POSTGRES_USER=myuser
      - POSTGRES_PASSWORD=mypass
      - POSTGRES_DB=mydb
    volumes:
      - pgdata:/var/lib/postgresql/data

volumes:
  pgdata:

Key Commands

# Start all services (in the background)
$ docker compose up -d
[+] Running 3/3
 ✔ Container myapp-db-1   Started
 ✔ Container myapp-api-1  Started
 ✔ Container myapp-web-1  Started
# Stop and remove all services
$ docker compose down
# Stop and remove services INCLUDING volumes (deletes data!)
$ docker compose down -v
# View running compose services
$ docker compose ps
NAME             IMAGE             STATUS          PORTS
myapp-db-1       postgres:15       Up 2 minutes    5432/tcp
myapp-api-1      myapp-api         Up 2 minutes    0.0.0.0:3000->3000/tcp
myapp-web-1      nginx:alpine      Up 2 minutes    0.0.0.0:8080->80/tcp
# View logs for all services
$ docker compose logs

# Follow logs for a specific service
$ docker compose logs -f api
# Rebuild and restart services
$ docker compose up -d --build
# Scale a service (run multiple instances)
$ docker compose up -d --scale api=3
# Execute a command in a running compose service
$ docker compose exec db psql -U myuser -d mydb

Full Example: Web App + Database

# docker-compose.yml — A WordPress site with MySQL
version: "3.8"

services:
  wordpress:
    image: wordpress:latest
    ports:
      - "8080:80"
    environment:
      WORDPRESS_DB_HOST: db
      WORDPRESS_DB_USER: wp_user
      WORDPRESS_DB_PASSWORD: wp_pass
      WORDPRESS_DB_NAME: wordpress
    volumes:
      - wp_data:/var/www/html
    depends_on:
      - db
    restart: unless-stopped

  db:
    image: mysql:8.0
    environment:
      MYSQL_DATABASE: wordpress
      MYSQL_USER: wp_user
      MYSQL_PASSWORD: wp_pass
      MYSQL_ROOT_PASSWORD: root_secret
    volumes:
      - db_data:/var/lib/mysql
    restart: unless-stopped

volumes:
  wp_data:
  db_data:
docker-compose vs docker compose

The older standalone docker-compose (with a hyphen) is a separate Python-based tool. Modern Docker includes Compose as a plugin: docker compose (with a space). They are functionally equivalent, but the plugin version is preferred going forward. This chapter uses the docker compose syntax.

14. Volumes — Persistent Data

By default, all data inside a container is lost when the container is removed. Volumes provide persistent storage that survives container restarts and removal.

Types of Storage

TypeSyntaxUse Case
Named volume-v mydata:/app/dataDatabase storage, persistent app data
Bind mount-v /host/path:/container/pathDevelopment (live code reloading)
tmpfs mount--tmpfs /tmpTemporary data that should not persist
 
# Create a named volume
$ docker volume create mydata
# Run a container with a named volume
$ docker run -d --name db -v mydata:/var/lib/postgresql/data postgres:15
# List all volumes
$ docker volume ls
DRIVER    VOLUME NAME
local     mydata
local     pgdata
# Inspect a volume (see where it's stored on the host)
$ docker volume inspect mydata
[{
    "CreatedAt": "2025-01-15T10:00:00Z",
    "Driver": "local",
    "Mountpoint": "/var/lib/docker/volumes/mydata/_data",
    "Name": "mydata"
}]
# Bind mount: map a host directory into the container
$ docker run -d --name dev-web \
  -v $(pwd)/src:/app/src \
  -p 3000:3000 \
  node:18-alpine npm start
# Read-only bind mount (container cannot write to it)
$ docker run -d -v /etc/config:/app/config:ro myapp
# Remove unused volumes
$ docker volume prune
Caution: docker compose down -v removes named volumes defined in the compose file. For databases, this means all your data will be deleted. Only use -v when you truly want a fresh start.

15. Networking Basics

Docker creates isolated networks so containers can communicate with each other and the outside world.

Network Types

DriverDescriptionUse Case
bridgeDefault. Containers on the same bridge can communicate.Single-host container communication
hostContainer shares the host's network stack.Performance-sensitive apps, no port mapping needed
noneNo networking at all.Completely isolated containers
overlayMulti-host networking for Docker Swarm.Clustered deployments
 
# List Docker networks
$ docker network ls
NETWORK ID     NAME      DRIVER    SCOPE
abc123def456   bridge    bridge    local
def456abc789   host      host      local
789abc123def   none      null      local
# Create a custom bridge network
$ docker network create my-network
# Run containers on the same network (they can find each other by name)
$ docker run -d --name api --network my-network node:18-alpine
$ docker run -d --name db --network my-network postgres:15

# From the 'api' container, you can now reach 'db' by hostname:
$ docker exec api ping db
PING db (172.18.0.3): 56 data bytes
64 bytes from 172.18.0.3: seq=0 ttl=64 time=0.089 ms
# Connect a running container to a network
$ docker network connect my-network existing-container
# Inspect a network (see connected containers)
$ docker network inspect my-network
# Port mapping recap: HOST_PORT:CONTAINER_PORT
$ docker run -d -p 8080:80 nginx      # Host 8080 → Container 80
$ docker run -d -p 127.0.0.1:8080:80 nginx  # Only localhost

         External traffic
       (http://localhost:3000)

On a custom network, containers can reach each other by container name (Docker provides built-in DNS). The -p flag creates a port mapping so external traffic can reach the container.

Common Mistake: Forgetting to expose ports. The EXPOSE instruction in a Dockerfile is documentation only — it does not actually publish the port. You must use -p with docker run (or ports: in Compose) to make a container reachable from outside.

16. Docker Cleanup

Docker can consume significant disk space over time with old images, stopped containers, and unused volumes. Regular cleanup is important.

# Nuclear option: remove ALL unused data (stopped containers, unused networks,
# dangling images, and build cache)
$ docker system prune
WARNING! This will remove:
  - all stopped containers
  - all networks not used by at least one container
  - all dangling images
  - unused build cache

Are you sure you want to continue? [y/N] y
Total reclaimed space: 2.3GB
# Include unused images too (not just dangling ones)
$ docker system prune -a
WARNING! This will remove:
  - all stopped containers
  - all networks not used by at least one container
  - all images without at least one container associated to them
  - all build cache
Total reclaimed space: 8.1GB
# See how much disk space Docker is using
$ docker system df
TYPE            TOTAL   ACTIVE  SIZE      RECLAIMABLE
Images          15      3       4.2GB     3.1GB (73%)
Containers      5       2       150MB     120MB (80%)
Local Volumes   8       3       1.5GB     800MB (53%)
Build Cache     20      0       500MB     500MB
# Remove specific resource types
$ docker container prune    # Remove stopped containers
$ docker image prune        # Remove dangling images
$ docker volume prune       # Remove unused volumes
$ docker network prune      # Remove unused networks
# Remove images older than 24 hours
$ docker image prune -a --filter "until=24h"
# Force prune without confirmation prompt
$ docker system prune -f
Danger: Volume Pruning

docker volume prune permanently deletes data in unnamed volumes that are not attached to any container. If you store database data in volumes, make sure you have backups before pruning. There is no undo.

Common Mistakes

Mistake 1: Running as root inside containers.

By default, many Docker images run processes as root. If an attacker exploits a vulnerability in your app, they have root access inside the container. Always create a non-root user in your Dockerfile:

RUN addgroup -S appgroup && adduser -S appuser -G appgroup
USER appuser
Mistake 2: Forgetting to expose or map ports.

Your container runs fine, but you cannot reach it from the browser. You need -p HOST:CONTAINER when running. EXPOSE in the Dockerfile alone does nothing for external access.

Mistake 3: Storing data inside the container without a volume.

If you write important data (database files, uploads) to the container filesystem, it will be lost when the container is removed. Always use volumes for persistent data.

Mistake 4: Using latest tag in production.

The latest tag is mutable — it can point to different images over time. Pin your images to specific versions (e.g., node:18.19-alpine instead of node:latest) for reproducible builds.

Mistake 5: Putting secrets in the Dockerfile or image.

Never put passwords, API keys, or tokens directly in a Dockerfile (ENV SECRET_KEY=abc123). Anyone who pulls the image can read them. Use environment variables at runtime, Docker secrets, or a secrets manager instead.

Security Warning: Running Untrusted Images

Running docker run with an image you did not build yourself is equivalent to running a program you downloaded from the internet. The container has access to any ports you map, any volumes you mount, and runs with the privileges you grant. Malicious images have been found on Docker Hub that:

  • Mine cryptocurrency using your CPU
  • Exfiltrate environment variables (including cloud credentials)
  • Install backdoors in mounted volumes
  • Scan your internal network

Always verify the source. Use official images, check the Dockerfile, and scan with docker scout or trivy.

Quizzes

Quick Quiz 1: What is the difference between docker stop and docker rm?
docker stop sends a SIGTERM signal to gracefully shut down a running container (it remains on disk in a "stopped" state). docker rm deletes a stopped container entirely from disk. You must stop a container before removing it, unless you use docker rm -f which forces both operations.
Quick Quiz 2: You built and ran a container but cannot access it from your browser at http://localhost:8080. The container logs show it is listening on port 3000. What went wrong and how do you fix it?
The port mapping is wrong or missing. You need to map the host port (8080) to the container port (3000). The correct flag is -p 8080:3000. A common mistake is writing -p 3000:8080 which maps host port 3000 to container port 8080 (reversed). Also verify the container is actually running with docker ps and that no firewall is blocking the port.
