Chapter 17: Git Basics

Git is the most widely used version control system in the world. Whether you are writing shell scripts, managing configuration files, or contributing to open-source projects, Git lets you track every change, collaborate with others, and undo mistakes with confidence. This chapter teaches you everything you need to get productive with Git on the Linux command line.

Prerequisites

You should be comfortable navigating the terminal (Chapter 2), working with files and directories (Chapter 3), and using a text editor like nano or vim (Chapter 4). No prior Git experience is needed.

1. What is Git?

Git is a distributed version control system (DVCS). It records every change you make to files over time, so you can recall any previous version whenever you need it. Created by Linus Torvalds in 2005 to manage the Linux kernel source code, Git is now the industry standard for software development.

Why Version Control Matters

  • Undo mistakes — accidentally deleted a paragraph or broke a script? Roll back to a working version.
  • Track history — see who changed what, when, and why.
  • Collaborate safely — multiple people can work on the same project without overwriting each other.
  • Branching — experiment with new features without affecting the stable version.
  • Backup — pushing to a remote repository means your code lives in multiple places.
The "Save Game" Analogy

Think of Git like a video game save system. Every time you commit, you create a save point. You can keep playing (making changes), and if something goes wrong you can load any previous save. You can even create parallel timelines (branches) to try different strategies without losing your main progress.

Mental Model: The Three Areas of Git

Git organizes your work into three areas:

  1. Working Directory — the actual files on your disk that you edit.
  2. Staging Area (Index) — a holding area where you prepare changes before saving them. Think of it as a "loading dock."
  3. Repository (.git/) — the permanent history of all your committed snapshots.
  Working Directory    Staging Area    Repository
  ┌──────────────┐    ┌───────────┐    ┌──────────┐
  │  Edit files   │──>│ git add    │──>│ git commit│
  │  (your work)  │    │ (prepare)  │    │ (save)    │
  └──────────────┘    └───────────┘    └──────────┘
         │                                    │
         │<───────────── git checkout ────────│

Every Git command moves data between these three areas. Once you understand this flow, everything else clicks into place.

2. Installing Git

Most Linux distributions come with Git pre-installed. If not, installing it takes one command.

Install on Debian/Ubuntu

$ sudo apt update
$ sudo apt install git

Install on Fedora/RHEL

$ sudo dnf install git

Install on Arch

$ sudo pacman -S git

Verify the Installation

$ git --version
git version 2.43.0

Initial Setup (Required)

Git needs to know who you are before you can commit. These settings are stored in ~/.gitconfig.

$ git config --global user.name "Your Name"
$ git config --global user.email "you@example.com"

# Optionally set your default editor
$ git config --global core.editor nano

# Set the default branch name to "main" (modern convention)
$ git config --global init.defaultBranch main

# Verify your settings
$ git config --list
user.name=Your Name
user.email=you@example.com
core.editor=nano
init.defaultbranch=main

3. git init — Create a New Repository

The git init command creates a brand-new Git repository in the current directory. It adds a hidden .git/ folder that stores all version-control metadata.

$ git init
Initialized empty Git repository in /home/user/project/.git/

What is .git/?

The .git/ directory is where Git stores everything: commit history, branches, configuration, and objects. If you delete this folder, you lose all version history (but keep your files).

$ ls -la .git/
total 40
drwxr-xr-x  7 user user 4096 Jan 15 10:00 .
drwxr-xr-x  3 user user 4096 Jan 15 10:00 ..
-rw-r--r--  1 user user   23 Jan 15 10:00 HEAD
drwxr-xr-x  2 user user 4096 Jan 15 10:00 branches
-rw-r--r--  1 user user   92 Jan 15 10:00 config
-rw-r--r--  1 user user   73 Jan 15 10:00 description
drwxr-xr-x  2 user user 4096 Jan 15 10:00 hooks
drwxr-xr-x  2 user user 4096 Jan 15 10:00 info
drwxr-xr-x  4 user user 4096 Jan 15 10:00 objects
drwxr-xr-x  4 user user 4096 Jan 15 10:00 refs

Examples

# Create a project and initialize Git
$ mkdir my-project && cd my-project
$ git init
Initialized empty Git repository in /home/user/my-project/.git/

# Initialize in a specific directory
$ git init /home/user/new-repo
Initialized empty Git repository in /home/user/new-repo/.git/

# Initialize with a custom default branch name
$ git init --initial-branch=main my-app
Initialized empty Git repository in /home/user/my-app/.git/

# Re-running git init on an existing repo is safe (does nothing harmful)
$ cd my-project
$ git init
Reinitialized existing Git repository in /home/user/my-project/.git/

# Create a bare repository (for servers — no working directory)
$ git init --bare shared-repo.git
Initialized empty Git repository in /home/user/shared-repo.git/
Warning

Never run git init inside your home directory (~) or root (/). This would try to track every file on your system. Always create a dedicated project directory first.

4. git clone — Clone an Existing Repository

Instead of starting from scratch, git clone copies an existing repository — including its entire history — to your machine.

$ git clone https://github.com/user/project.git
Cloning into 'project'...
remote: Enumerating objects: 234, done.
remote: Counting objects: 100% (234/234), done.
remote: Compressing objects: 100% (156/156), done.
Receiving objects: 100% (234/234), 1.24 MiB | 3.40 MiB/s, done.

Examples

# Clone via HTTPS
$ git clone https://github.com/torvalds/linux.git

# Clone via SSH (requires SSH key setup)
$ git clone git@github.com:user/project.git

# Clone into a specific directory name
$ git clone https://github.com/user/project.git my-local-name

# Shallow clone (only latest commit — faster for large repos)
$ git clone --depth 1 https://github.com/torvalds/linux.git

# Clone a specific branch
$ git clone --branch develop https://github.com/user/project.git

# Clone and also initialize submodules
$ git clone --recurse-submodules https://github.com/user/project.git

5. git status — Check the Working Tree

The git status command shows the current state of your repository: which files are modified, which are staged, and which are untracked. Run it often — it is your GPS in Git.

Examples

# Clean working directory (nothing to commit)
$ git status
On branch main
nothing to commit, working tree clean

# Untracked file (new file Git does not know about yet)
$ touch newfile.txt
$ git status
On branch main
Untracked files:
  (use "git add <file>..." to include in what will be committed)
        newfile.txt

nothing added to commit but untracked files present (use "git add" to track)

# Modified file (tracked file changed but not staged)
$ echo "update" >> README.md
$ git status
On branch main
Changes not staged for commit:
  (use "git add <file>..." to update what will be committed)
        modified:   README.md

# Staged file (ready to be committed)
$ git add README.md
$ git status
On branch main
Changes to be committed:
  (use "git restore --staged <file>..." to unstage)
        modified:   README.md

# Mix of staged, modified, and untracked files
$ git status
On branch main
Changes to be committed:
        modified:   README.md
Changes not staged for commit:
        modified:   app.py
Untracked files:
        notes.txt

# Short format for quick glances
$ git status -s
M  README.md
 M app.py
?? notes.txt

# Show branch info in short format
$ git status -sb
## main...origin/main
M  README.md
 M app.py
?? notes.txt

# Check status of a specific path
$ git status src/
On branch main
Changes not staged for commit:
        modified:   src/index.js
Tip: Read the Status Codes

In git status -s, the left column is the staging area and the right column is the working directory. M = modified, A = added, D = deleted, ?? = untracked, R = renamed.

6. git add — Stage Files

The git add command moves changes from the working directory into the staging area. Only staged changes are included in the next commit.

Examples

# Stage a specific file
$ git add README.md

# Stage multiple specific files
$ git add file1.txt file2.txt file3.txt

# Stage all changes in the current directory (new, modified, deleted)
$ git add .

# Stage all changes in the entire repository
$ git add -A

# Stage only modified and deleted files (not new/untracked)
$ git add -u

# Stage files matching a pattern
$ git add *.py
$ git add src/

# Interactive staging — choose chunks of changes to stage
$ git add -p
diff --git a/app.py b/app.py
@@ -1,3 +1,5 @@
+import os
+
 def main():
     print("hello")
Stage this hunk [y,n,q,a,d,/,e,?]?

# Verify what you staged
$ git add README.md
$ git status
Changes to be committed:
        modified:   README.md
Why Does the Staging Area Exist?

The staging area gives you fine-grained control over commits. Instead of committing every change at once, you can stage and commit related changes together. For example, you might fix a bug in one file and add a feature in another — you can commit the bug fix first, then the feature separately. This keeps your history clean and meaningful.

Be Careful with git add .

Running git add . stages everything, including files you may not want to commit (log files, build artifacts, secrets). Always check git status before committing, and use a .gitignore file to exclude unwanted files.

7. git commit — Save Snapshots

The git commit command takes everything in the staging area and saves it as a permanent snapshot in the repository. Each commit has a unique SHA-1 hash, an author, a timestamp, and a message describing the change.

Examples

# Basic commit with a message
$ git commit -m "Add user login feature"
[main 3a7f2e1] Add user login feature
 2 files changed, 45 insertions(+), 3 deletions(-)

# Commit with a multi-line message (opens your editor)
$ git commit

# Stage and commit all tracked (modified/deleted) files in one step
$ git commit -am "Fix typo in README"

# Amend the most recent commit (fix message or add forgotten files)
$ git add forgotten-file.txt
$ git commit --amend -m "Add user login feature (with validation)"

# Commit with a detailed multi-line message inline
$ git commit -m "Add search feature" -m "Implements full-text search using grep. Includes unit tests and updated documentation."

# Commit only specific staged files
$ git add src/login.py tests/test_login.py
$ git commit -m "Add login module with tests"

# Create an empty commit (useful for triggering CI/CD)
$ git commit --allow-empty -m "Trigger rebuild"

# See what would be committed (dry run)
$ git diff --cached --stat
 README.md  | 5 +++--
 app.py     | 12 ++++++++++++
 2 files changed, 15 insertions(+), 2 deletions(-)

Writing Good Commit Messages

RuleExample
Use the imperative mood ("Add", not "Added")Add user authentication
Keep the subject line under 50 charactersFix null pointer in login handler
Separate subject from body with a blank line(Use your editor for multi-line)
Explain why, not just whatBody: "Users reported crashes when..."
Reference issue numbers when relevantFix login crash (closes #42)
Tip

A good commit message answers: "If I apply this commit, it will..." followed by your subject line. For example: "If I apply this commit, it will fix the null pointer in the login handler."

Examples

9. git diff — See Changes

The git diff command shows exactly what changed, line by line. It is essential for reviewing your work before committing.

Examples

# Show unstaged changes (working directory vs staging area)
$ git diff
diff --git a/app.py b/app.py
index 1234567..abcdefg 100644
--- a/app.py
+++ b/app.py
@@ -1,3 +1,5 @@
+import os
+import sys

 def main():
-    print("hello")
+    print("hello world")

# Show staged changes (staging area vs last commit)
$ git diff --cached
$ git diff --staged      # same thing

# Show ALL changes (both staged and unstaged vs last commit)
$ git diff HEAD

# Diff between two commits
$ git diff 3a7f2e1 1b2c3d4

# Diff between branches
$ git diff main feature

# Diff for a specific file only
$ git diff -- README.md

# Show only names of changed files
$ git diff --name-only
app.py
README.md

# Show a summary of changes (insertions/deletions)
$ git diff --stat
 app.py    | 4 ++--
 README.md | 2 +-
 2 files changed, 3 insertions(+), 3 deletions(-)
Reading Diff Output

Lines starting with + (green) are additions. Lines starting with - (red) are deletions. Lines with no prefix are context (unchanged). The @@ header tells you the line numbers affected.

10. git push / git pull — Sync with Remote

Git repositories can live on remote servers (GitHub, GitLab, etc.). git push uploads your commits, and git pull downloads commits from others.

What is a Remote?

A remote is a copy of your repository hosted somewhere else. When you git clone, Git automatically names the source origin. You can add multiple remotes (e.g., upstream for the original project you forked from).

git push Examples

# Push to origin (after clone, this is the default remote)
$ git push origin main

# Set upstream tracking and push (first time pushing a new branch)
$ git push -u origin feature-login
Branch 'feature-login' set up to track remote branch 'feature-login' from 'origin'.

# After -u is set, just use:
$ git push

# Push all branches
$ git push --all origin

# Push tags
$ git push origin --tags

git pull Examples

# Pull latest changes from the tracked remote branch
$ git pull
remote: Enumerating objects: 5, done.
remote: Counting objects: 100% (5/5), done.
Updating 3a7f2e1..9b8c7d6
Fast-forward
 README.md | 3 ++-
 1 file changed, 2 insertions(+), 1 deletion(-)

# Pull from a specific remote and branch
$ git pull origin main

# Pull with rebase instead of merge (cleaner history)
$ git pull --rebase origin main

# See what would be pulled without actually pulling
$ git fetch origin
$ git log HEAD..origin/main --oneline
9b8c7d6 Update API docs
5e4f3a2 Fix login bug
Always Pull Before You Push

If someone else has pushed changes since your last pull, your push will be rejected. Always git pull first to incorporate their changes, resolve any conflicts, then push.

11. git branch — Manage Branches

Branches let you work on different features or fixes in isolation. The default branch is usually called main (or master in older repos).

Examples

# List local branches (current branch marked with *)
$ git branch
* main
  feature-login
  bugfix-header

# List all branches (local + remote)
$ git branch -a
* main
  feature-login
  remotes/origin/main
  remotes/origin/develop

# List remote branches only
$ git branch -r

# Create a new branch (does not switch to it)
$ git branch feature-search

# Create a branch from a specific commit
$ git branch hotfix 3a7f2e1

# Rename a branch
$ git branch -m old-name new-name

# Delete a branch (only if fully merged)
$ git branch -d feature-login
Deleted branch feature-login (was 5c4d3e2).

# Force-delete a branch (even if not merged — use with caution)
$ git branch -D abandoned-experiment

# Show which branches are merged into current branch
$ git branch --merged

# Show which branches are NOT merged
$ git branch --no-merged

12. git checkout / git switch — Switch Branches

To work on a branch, you need to switch to it. The modern command is git switch (introduced in Git 2.23). The older git checkout still works and is more widely known.

Examples

# Switch to an existing branch (modern)
$ git switch feature-login

# Switch to an existing branch (classic)
$ git checkout feature-login

# Create a new branch and switch to it (modern)
$ git switch -c feature-search
Switched to a new branch 'feature-search'

# Create a new branch and switch to it (classic)
$ git checkout -b feature-search

# Switch back to the previous branch
$ git switch -
$ git checkout -     # same thing

# Discard changes to a specific file (classic checkout)
$ git checkout -- app.py    # revert app.py to last committed version

# Modern equivalent for discarding changes
$ git restore app.py
checkout vs switch vs restore

git checkout does two things: switches branches and restores files. This was confusing, so Git 2.23 split it into git switch (branches) and git restore (files). Use the newer commands when possible.

13. git merge — Merge Branches

Merging integrates changes from one branch into another. This is how feature work gets incorporated into the main branch.

Fast-Forward vs Three-Way Merge

TypeWhen It HappensResult
Fast-forwardMain has no new commits since the branch was createdGit just moves the pointer forward; no merge commit
Three-way mergeBoth branches have new commitsGit creates a merge commit that combines both histories

Examples

# Merge feature branch into main
$ git switch main
$ git merge feature-login
Updating 3a7f2e1..5c4d3e2
Fast-forward
 src/login.py | 45 +++++++++++++++++++++++++++++++++++++++++++++
 1 file changed, 45 insertions(+)

# Force a merge commit even for fast-forward
$ git merge --no-ff feature-login
Merge made by the 'ort' strategy.

# Merge with a custom commit message
$ git merge feature-search -m "Merge search feature into main"

# Abort a merge in progress (if something went wrong)
$ git merge --abort

# Preview what a merge would change (without actually merging)
$ git diff main...feature-login

# Merge a specific commit (cherry-pick is better for this)
$ git merge 5c4d3e2

Handling Merge Conflicts (Step by Step)

A conflict happens when both branches changed the same lines in the same file. Git cannot decide which version to keep, so it asks you to resolve it manually.

# Step 1: Attempt the merge
$ git merge feature-login
Auto-merging src/app.py
CONFLICT (content): Merge conflict in src/app.py
Automatic merge failed; fix conflicts and then commit the result.

# Step 2: See which files have conflicts
$ git status
Unmerged paths:
  both modified:   src/app.py

# Step 3: Open the conflicted file — look for conflict markers
$ cat src/app.py
<<<<<<< HEAD
    print("Welcome, user!")
=======
    print("Hello, user! Welcome back.")
>>>>>>> feature-login

# Step 4: Edit the file — keep what you want, remove the markers
$ nano src/app.py
# (You decide: keep one version, combine both, or write something new)

# Step 5: Mark the conflict as resolved by staging the file
$ git add src/app.py

# Step 6: Complete the merge with a commit
$ git commit -m "Merge feature-login, resolve greeting conflict"
Conflict Markers Must Be Removed

Never commit files that still contain <<<<<<<, =======, or >>>>>>> markers. These are not valid code and will cause errors.

14. git stash — Temporarily Shelve Changes

Sometimes you need to switch branches but have uncommitted work. git stash saves your changes temporarily and gives you a clean working directory.

Examples

# Save current changes to the stash
$ git stash
Saved working directory and index state WIP on main: 3a7f2e1 Add login feature

# Stash with a descriptive message
$ git stash push -m "halfway through search feature"
Saved working directory and index state On main: halfway through search feature

# List all stashes
$ git stash list
stash@{0}: On main: halfway through search feature
stash@{1}: WIP on main: 3a7f2e1 Add login feature

# Restore the most recent stash (and remove it from the stash list)
$ git stash pop
On branch main
Changes not staged for commit:
        modified:   src/search.py
Dropped refs/stash@{0}

# Restore a stash but keep it in the list (in case you need it again)
$ git stash apply

# Restore a specific stash by index
$ git stash apply stash@{1}

# Show what a stash contains (without applying it)
$ git stash show
 src/search.py | 24 ++++++++++++++++++++++--
 1 file changed, 22 insertions(+), 2 deletions(-)

# Show the full diff of a stash
$ git stash show -p

# Delete a specific stash
$ git stash drop stash@{1}
Dropped stash@{1}

# Delete ALL stashes
$ git stash clear

# Stash including untracked files
$ git stash -u
Stash Workflow

A common pattern: you are working on feature A, but need to fix an urgent bug. Stash your feature A changes, switch to main, fix the bug, commit, switch back, and pop your stash to resume where you left off.

15. .gitignore — Excluding Files from Git

A .gitignore file tells Git which files and directories to ignore. Ignored files will not show up in git status and will not be staged by git add ..

How It Works

Create a file called .gitignore in your project root. Each line is a pattern matching files to exclude.

# .gitignore example for a Python project

# Byte-compiled files
__pycache__/
*.pyc
*.pyo

# Virtual environments
venv/
.env/

# IDE settings
.vscode/
.idea/
*.swp
*.swo
*~

# OS files
.DS_Store
Thumbs.db

# Logs
*.log
logs/

# Environment variables (secrets!)
.env
.env.local

# Build output
dist/
build/
*.egg-info/

# Dependency directories
node_modules/

Pattern Rules

PatternWhat It Matches
*.logAll files ending in .log
logs/The entire logs directory
/debug.logOnly debug.log in the root (not src/debug.log)
doc/**/*.pdfAll PDFs inside doc/ at any depth
!important.logException: do NOT ignore important.log
#Comment (ignored by Git)

Common Commands

# Check if a file is ignored
$ git check-ignore -v debug.log
.gitignore:5:*.log    debug.log

# List all ignored files
$ git status --ignored

# Stop tracking a file that was already committed (but keep the file)
$ git rm --cached secret.env
$ echo "secret.env" >> .gitignore
$ git commit -m "Remove secret.env from tracking"

# Global gitignore for your machine (applies to all repos)
$ git config --global core.excludesFile ~/.gitignore_global
Secrets and .gitignore

Always add .env, credentials files, and API keys to .gitignore before your first commit. If you accidentally commit a secret, it stays in the Git history even after you delete the file. You would need to rewrite history to fully remove it.

Git Workflow Diagram

A Typical Git Workflow

Here is a step-by-step workflow you will repeat hundreds of times:

  1. Pull latest changes        git pull origin main
  2. Create a feature branch     git switch -c feature-xyz
  3. Make changes                (edit files)
  4. Check what changed          git status / git diff
  5. Stage changes               git add file1.py file2.py
  6. Commit                      git commit -m "Add feature xyz"
  7. Push the branch             git push -u origin feature-xyz
  8. Create a Pull Request       (on GitHub/GitLab)
  9. After review, merge         git switch main && git pull
 10. Delete feature branch       git branch -d feature-xyz

This is called the feature branch workflow and is the most common pattern in professional development.

The Complete Git Data Flow
  Remote Repository (GitHub, GitLab, etc.)
         |            ^
    git pull/     git push
    git fetch        |
         |            |
         v            |
  Local Repository (.git/)
         |            ^
    git checkout/ git commit
    git restore      |
         |            |
         v            |
     Staging Area (Index)
         ^            ^
         |        git add
    git restore      |
    --staged         |
         |            |
         v            |
     Working Directory (your files)

Common Mistakes & How to Fix Them

Mistake 1: Committed to the Wrong Branch

You made a commit on main but meant to commit on a feature branch.

# Undo the commit (keep changes in working directory)
$ git reset --soft HEAD~1

# Create the correct branch and switch to it
$ git switch -c feature-xyz

# Your changes are still staged — just commit again
$ git commit -m "Add feature xyz"

Mistake 2: Forgot to Pull Before Working

You made local commits, then git push is rejected because the remote has new commits.

# Option A: Pull with rebase (puts your commits on top)
$ git pull --rebase origin main

# Option B: Regular pull (creates a merge commit)
$ git pull origin main

Mistake 3: Accidentally Staged a File

# Unstage a file (keep changes in working directory)
$ git restore --staged secret.env

# Older syntax
$ git reset HEAD secret.env

Mistake 4: Need to Undo the Last Commit

# Undo commit, keep changes staged
$ git reset --soft HEAD~1

# Undo commit, keep changes in working directory (unstaged)
$ git reset --mixed HEAD~1

# Undo commit AND discard all changes (DANGEROUS)
$ git reset --hard HEAD~1
Warning: git reset --hard Is Destructive

Using --hard permanently discards uncommitted changes. There is no undo. Only use it when you are certain you want to throw away your work.

Mistake 5: Committed a Secret (Password, API Key)

# If it was the very last commit and you haven't pushed yet:
$ git reset --soft HEAD~1
$ git rm --cached secret.env
$ echo "secret.env" >> .gitignore
$ git add .gitignore
$ git commit -m "Remove secret, update gitignore"

# If already pushed, you need to rotate the secret immediately
# and use tools like git-filter-repo to rewrite history

Exercise 1: Your First Repository

Practice the full Git workflow from scratch:

  1. Create a new directory called git-practice and initialize a Git repo inside it.
  2. Create a file called hello.sh with the content echo "Hello, Git!".
  3. Check the status, stage the file, and make your first commit.
  4. Modify hello.sh to say echo "Hello, Git! Version 2".
  5. View the diff, stage, and commit again with a good message.
  6. View the log to see both commits.
Show Solution 
$ mkdir git-practice && cd git-practice
$ git init
$ echo 'echo "Hello, Git!"' > hello.sh
$ git status
$ git add hello.sh
$ git commit -m "Add hello script"

$ sed -i 's/Hello, Git!/Hello, Git! Version 2/' hello.sh
$ git diff
$ git add hello.sh
$ git commit -m "Update greeting to version 2"

a1b2c3d Update greeting to version 2

Exercise 2: Branching and Merging

Practice creating branches and merging them:

  1. Starting from the repo in Exercise 1, create a branch called add-goodbye.
  2. Switch to the new branch and add a file goodbye.sh with echo "Goodbye!".
  3. Commit the new file on the add-goodbye branch.
  4. Switch back to main and verify goodbye.sh does not exist there.
  5. Merge add-goodbye into main.
  6. Verify goodbye.sh now exists on main, then delete the feature branch.

Exercise 3: Resolving a Merge Conflict

Deliberately create and resolve a merge conflict:

  1. On main, edit hello.sh to say echo "Hello from main!" and commit.
  2. Create a branch called feature from the commit before your main change (use git log to find the hash).
  3. On feature, edit hello.sh to say echo "Hello from feature!" and commit.
  4. Switch to main and try to merge feature.
  5. Resolve the conflict by combining both greetings, then complete the merge.
Show Solution 
# On main, make a change
$ echo 'echo "Hello from main!"' > hello.sh
$ git add hello.sh
$ git commit -m "Update greeting on main"

# Find the commit before this one
$ git log --oneline -3
c1d2e3f Update greeting on main
a1b2c3d Update greeting to version 2
e4f5a6b Add hello script

# Create feature branch from the previous commit
$ git branch feature a1b2c3d
$ git switch feature
$ echo 'echo "Hello from feature!"' > hello.sh
$ git add hello.sh
$ git commit -m "Update greeting on feature"

# Merge and get a conflict
$ git switch main
$ git merge feature
CONFLICT (content): Merge conflict in hello.sh

# Resolve: combine both greetings
$ cat > hello.sh <<'EOF'
echo "Hello from main!"
echo "Hello from feature!"
EOF
$ git add hello.sh
$ git commit -m "Merge feature: combine greetings"

Quizzes

Quick Quiz: What is the difference between git add . and git add -u?
git add . stages all changes in the current directory: new (untracked) files, modified files, and deleted files. git add -u stages only modified and deleted files that are already tracked — it ignores untracked (new) files. Use git add -u when you want to avoid accidentally staging new files you have not reviewed.
Quick Quiz: You are on the main branch and realize your last commit should have been on a feature branch. What commands fix this without losing your work?
Run git reset --soft HEAD~1 to undo the commit while keeping all changes staged. Then run git switch -c feature-branch to create and switch to a new branch. Finally, run git commit -m "your message" to recommit the changes on the correct branch. The --soft flag is key: it undoes the commit but preserves your work in the staging area.
