Chapter 7: Processes & Jobs

Every time you run a command, open an application, or start a service, Linux creates a process. Understanding processes is essential for managing your system: you need to know what is running, how to stop misbehaving programs, how to run tasks in the background, and how to control resource usage. This chapter covers everything a beginner needs to know about processes and job control.

1. What is a Process?

Mental Model: Processes

Think of your Linux system as an office building. Every running program is a worker (process) with their own desk (memory), employee badge number (PID — Process ID), and a manager they report to (parent process). The building manager is init or systemd (PID 1), and every worker ultimately reports up to them.

When you type a command in the terminal, the shell (your current process) creates a child process to run that command. When the command finishes, the child process exits and reports back to the parent.

Key Concepts

  • PID (Process ID) — A unique number assigned to every running process. No two processes share the same PID at the same time.
  • PPID (Parent Process ID) — The PID of the process that started this one. Every process has a parent (except PID 1).
  • UID — The user ID of the person who started the process. Determines what the process can access.
  • Process States — A process is always in one of several states:
    • Running (R) — Currently executing on the CPU or ready to run.
    • Sleeping (S) — Waiting for something (input, a timer, a resource).
    • Stopped (T) — Paused, usually by a signal like Ctrl+Z.
    • Zombie (Z) — Finished executing but its parent has not yet read its exit status.
    • Dead (X) — Being cleaned up (you rarely see this).

2. ps — List Processes

The ps command gives you a snapshot of currently running processes. Unlike top, it does not update in real time — it shows you the state at the moment you run it.

Basic usage — your own processes

$ ps
  PID TTY          TIME CMD
 2451 pts/0    00:00:00 bash
 2489 pts/0    00:00:00 ps

By default, ps shows only processes belonging to your current terminal session.

Show all processes (BSD style) — ps aux

$ ps aux
USER       PID %CPU %MEM    VSZ   RSS TTY      STAT START   TIME COMMAND
root         1  0.0  0.1 169344 13200 ?        Ss   09:00   0:03 /sbin/init
root         2  0.0  0.0      0     0 ?        S    09:00   0:00 [kthreadd]
root       312  0.0  0.1  45892  8456 ?        Ss   09:00   0:01 /lib/systemd/systemd-journald
alice     2451  0.0  0.0  21384  5248 pts/0    Ss   10:15   0:00 -bash
alice     2489  0.0  0.0  37092  3344 pts/0    R+   10:22   0:00 ps aux
www-data  1087  0.1  0.5 272816 41200 ?        S    09:01   0:12 /usr/sbin/apache2 -k start
mysql     1124  0.5  2.3 1234567 187000 ?      Sl   09:01   1:45 /usr/sbin/mysqld
root       998  0.0  0.0  72296  6712 ?        Ss   09:01   0:00 /usr/sbin/sshd -D

Column breakdown: USER = who owns the process, PID = process ID, %CPU = CPU usage, %MEM = memory usage, VSZ = virtual memory (KB), RSS = physical memory (KB), TTY = terminal (? means no terminal, i.e. a daemon), STAT = state code, START = when it started, TIME = CPU time consumed, COMMAND = the command that launched the process.

Show all processes (System V style) — ps -ef

$ ps -ef
UID        PID  PPID  C STIME TTY          TIME CMD
root         1     0  0 09:00 ?        00:00:03 /sbin/init
root         2     1  0 09:00 ?        00:00:00 [kthreadd]
alice     2451  2449  0 10:15 pts/0    00:00:00 -bash
alice     2500  2451  0 10:24 pts/0    00:00:00 ps -ef

The -ef format shows PPID (parent PID), which is very useful for understanding which process launched which.

Processes for a specific user

Filter with grep

$ ps aux | grep nginx

www-data  1056  0.0  0.1  63240  9100 ?        S    09:01   0:02 nginx: worker process

Notice the last line is the grep command itself. To exclude it:

$ ps aux | grep [n]ginx
root      1055  0.0  0.1  62816  8200 ?        Ss   09:01   0:00 nginx: master process /usr/sbin/nginx
www-data  1056  0.0  0.1  63240  9100 ?        S    09:01   0:02 nginx: worker process
www-data  1057  0.0  0.1  63240  8800 ?        S    09:01   0:01 nginx: worker process

The bracket trick [n]ginx makes the regex not match the grep command itself.

3. top — Live Process Monitor

top is a real-time, continuously updating view of system processes. It shows CPU and memory usage, load averages, and lets you interact with processes.

$ top
top - 10:45:23 up  1:45,  2 users,  load average: 0.52, 0.38, 0.29
Tasks: 186 total,   2 running, 183 sleeping,   0 stopped,   1 zombie
%Cpu(s):  5.2 us,  1.8 sy,  0.0 ni, 92.3 id,  0.5 wa,  0.0 hi,  0.2 si,  0.0 st
MiB Mem :   7953.4 total,   3241.2 free,   2567.8 used,   2144.4 buff/cache
MiB Swap:   2048.0 total,   2048.0 free,      0.0 used.   4892.3 avail Mem

  PID USER      PR  NI    VIRT    RES    SHR S  %CPU  %MEM     TIME+ COMMAND
 3201 alice     20   0 2345678 253412 102400 R  45.2   3.1   2:34.56 firefox
 1124 mysql     20   0 1234567 187000  28416 S   2.3   2.3   1:45.12 mysqld
 1087 www-data  20   0  272816  41200  22528 S   0.5   0.5   0:12.03 apache2
 2548 alice     20   0   45892  62144  12288 S   0.3   0.8   0:05.91 python3
    1 root      20   0  169344  13200   8576 S   0.0   0.2   0:03.22 systemd

Reading the top display

  • Load average (0.52, 0.38, 0.29) — Average number of processes waiting to run over the last 1, 5, and 15 minutes. On a single-core system, 1.0 means fully loaded. On a 4-core system, 4.0 means fully loaded.
  • us — User space CPU time (your programs).
  • sy — System/kernel CPU time.
  • ni — Nice'd (re-prioritized) processes.
  • id — Idle CPU time (higher is better).
  • wa — Time waiting for I/O (high values suggest disk bottleneck).
  • PR — Priority. NI — Nice value (-20 to 19).
  • VIRT — Total virtual memory. RES — Resident (physical) memory. SHR — Shared memory.

Key commands inside top

$ top -b -n 1 | head -20       # One snapshot, first 20 lines
$ top -b -n 5 -d 2 > top.log   # 5 snapshots, 2 sec apart, save to file

4. htop — Interactive Process Monitor

htop is a more modern, user-friendly alternative to top. It provides color-coded output, mouse support, and easier navigation. You may need to install it: sudo apt install htop.

  F1Help  F2Setup  F3Search  F4Filter  F5Tree  F6SortBy  F7Nice-  F8Nice+  F9Kill  F10Quit

htop navigation and features

  • Arrow keys — Scroll through the process list.
  • F3 or / — Search for a process by name.
  • F4 or \ — Filter: only show processes matching a pattern.
  • F5 — Tree view: shows parent-child relationships visually.
  • F6 — Choose which column to sort by.
  • F7 / F8 — Decrease / increase nice value (change priority).
  • F9 — Send a signal (kill) to the selected process. A menu of signals appears.
  • F10 or q — Quit htop.
  • Space — Tag (select) a process. You can tag multiple processes and then kill them all at once.
  • u — Filter by user.
  • t — Toggle tree view.
  • H — Toggle hiding of user threads.
  • K — Toggle hiding of kernel threads.

5. pgrep — Find Processes by Name

pgrep searches for processes by name (or other attributes) and returns their PIDs. It is cleaner than ps aux | grep because it never matches itself.

$ pgrep firefox
3201

$ pgrep -l firefox          # -l = show name alongside PID
3201 firefox

$ pgrep -a firefox          # -a = show full command line
3201 /usr/lib/firefox/firefox -new-window

$ pgrep -u alice            # All PIDs owned by alice
2451
2510
2530
2548
3201

$ pgrep -c bash             # -c = count matching processes
3

$ pgrep -u root -l sshd     # Find sshd processes owned by root
998 sshd
2449 sshd

$ pgrep -x bash             # -x = exact match only (not "bash-helper")
2451
2530
Signals — How Processes Communicate

Signals are the way the operating system (and you) communicate with running processes. Think of it like this:

  • SIGTERM (15) is like politely tapping someone on the shoulder and saying "Please finish up and leave." The process can clean up, save data, and shut down gracefully.
  • SIGKILL (9) is like pulling the power plug. The process has no chance to clean up. Data may be lost. Use this only as a last resort.
  • SIGINT (2) is like pressing Ctrl+C — "Please stop what you are doing."
  • SIGHUP (1) is like telling a process "Your terminal went away." Many daemons reload their configuration when they receive this signal.

6. kill — Send Signals to Processes

Despite its name, kill does not always kill a process. It sends a signal to a process. The default signal is SIGTERM (15), which asks the process to terminate gracefully.

Common signals reference table

SignalNumberNameDescriptionCan be caught?
SIGHUP1Hang UpTerminal closed or config reload for daemonsYes
SIGINT2InterruptSame as pressing Ctrl+CYes
SIGQUIT3QuitLike SIGINT but produces a core dumpYes
SIGKILL9KillForce kill — process cannot ignore thisNo
SIGTERM15TerminatePolite request to stop (default signal)Yes
SIGSTOP19StopPause the process (like Ctrl+Z but cannot be caught)No
SIGTSTP20Terminal StopCtrl+Z — suspend the foreground processYes
SIGCONT18ContinueResume a stopped processYes

Examples

$ kill 3201                 # Send SIGTERM (default) to PID 3201

$ kill -15 3201             # Same as above, explicit SIGTERM

$ kill -SIGTERM 3201        # Same, using signal name

$ kill -9 3201              # SIGKILL: force kill (last resort!)

$ kill -STOP 3201           # Pause (freeze) the process

$ kill -CONT 3201           # Resume the paused process

$ kill -HUP 998             # Tell sshd to reload its configuration

$ kill -l                   # List all available signal names
 1) SIGHUP       2) SIGINT       3) SIGQUIT      4) SIGILL       5) SIGTRAP
 6) SIGABRT      7) SIGBUS       8) SIGFPE       9) SIGKILL     10) SIGUSR1
11) SIGSEGV     12) SIGUSR2     13) SIGPIPE     14) SIGALRM     15) SIGTERM
...
Never use kill -9 as your first resort!

Always try kill PID (SIGTERM) first and wait a few seconds. SIGTERM lets the process clean up: save files, close database connections, remove temporary files, and notify child processes. kill -9 yanks the rug out immediately — the process has zero chance to tidy up. This can lead to:

  • Corrupted files or databases
  • Orphaned child processes
  • Leftover lock files that prevent the program from restarting
  • Lost unsaved data

The escalation order should be: kill PID → wait 5 seconds → kill -15 PID → wait 5 seconds → kill -9 PID

7. killall — Kill Processes by Name

killall sends a signal to all processes matching a given name. This is convenient but requires caution — you might kill more processes than intended.

$ killall firefox           # SIGTERM to all firefox processes

$ killall -9 firefox        # Force kill all firefox processes

$ killall -u alice python3  # Kill only alice's python3 processes

$ killall -i firefox        # Interactive: confirm each kill
Kill firefox(3201) ? (y/N) y
Kill firefox(3245) ? (y/N) n

$ killall -v nginx          # Verbose: report what was killed
Killed nginx(1055) with signal 15
Killed nginx(1056) with signal 15
Killed nginx(1057) with signal 15
Warning: killall behaves differently on some Unix systems!

On Linux, killall kills processes by name. On some older Solaris and Unix systems, killall kills every single process on the system. If you are on an unfamiliar system, always use pkill instead, or verify with man killall first.

8. pkill — Kill Processes by Pattern

pkill works like pgrep but sends a signal instead of printing PIDs. It matches process names using patterns, which makes it flexible.

$ pkill firefox             # SIGTERM to processes matching "firefox"

$ pkill -9 firefox          # SIGKILL all matching processes

$ pkill -u alice            # Kill all processes owned by user alice

$ pkill -f "python3 server.py"  # -f = match against full command line

$ pkill -x bash             # -x = exact name match only
pgrep + pkill: the safe pattern

Before using pkill, run pgrep -a with the same pattern to see what would be affected. This prevents accidentally killing the wrong processes.

$ pgrep -a "python3"        # Preview: what will be killed?
2548 python3 server.py
2590 python3 backup_script.py
$ pkill -f "python3 server.py"  # Now kill only the one you want

9. jobs — List Background Jobs

When you run commands in your terminal, they normally run in the foreground — they take over your terminal until they finish. Job control lets you move commands to the background, pause them, and resume them.

$ sleep 300 &               # Start a job in the background
[1] 4001
$ sleep 600 &               # Start another background job
[2] 4002
$ vim notes.txt              # Start vim, then press Ctrl+Z to suspend
[3]+  Stopped                 vim notes.txt
$ jobs
[1]   Running                 sleep 300 &
[2]-  Running                 sleep 600 &
[3]+  Stopped                 vim notes.txt

The output shows:

  • [1], [2], [3] — Job numbers (different from PIDs).
  • + — The most recent (current) job. - — The previous job.
  • Running — Job is active in the background.
  • Stopped — Job is paused (suspended).
$ jobs -l                   # -l = show PIDs alongside job numbers
[1]   4001 Running                 sleep 300 &
[2]-  4002 Running                 sleep 600 &
[3]+  4010 Stopped                 vim notes.txt

10. bg — Resume a Job in the Background

If you suspended a job with Ctrl+Z, you can resume it in the background using bg. The job continues running, but your terminal is free for other commands.

$ python3 long_task.py      # Running in foreground... press Ctrl+Z
^Z
[1]+  Stopped                 python3 long_task.py
$ bg                        # Resume it in the background
[1]+ python3 long_task.py &
$                           # Terminal is free again!

$ bg %2                     # Resume specifically job number 2
[2]+ sleep 600 &

11. fg — Bring a Job to the Foreground

fg brings a background or stopped job back to the foreground so you can interact with it directly.

$ fg                        # Bring the most recent job to foreground
vim notes.txt               # You are back inside vim

$ fg %1                     # Bring job number 1 to foreground
sleep 300

$ fg %?server               # Bring the job whose command contains "server"
python3 server.py

12. & — Run a Command in the Background

Appending & to any command starts it in the background immediately, returning control to your terminal.

$ cp -r /data/backup /mnt/external/ &
[1] 4100
$                           # Terminal is free while copy runs

$ find / -name "*.log" -size +100M > big_logs.txt 2>/dev/null &
[1] 4150
$                           # Long search runs in background

$ python3 web_server.py &
[1] 4200
$ curl http://localhost:8080   # You can use the terminal while the server runs
Hello, World!
Background output can be messy

Background processes still print to your terminal by default. Redirect their output to keep things clean:

$ ./noisy_script.sh > output.log 2>&1 &
[1] 4250

This sends both stdout and stderr to output.log, keeping your terminal clear.

13. nohup — Keep Running After Logout

When you close your terminal or log out of an SSH session, all processes in that session receive SIGHUP and typically die. nohup makes a process immune to the hangup signal, so it survives after you disconnect.

$ nohup python3 long_task.py &
[1] 4300
nohup: ignoring input and appending output to 'nohup.out'

By default, nohup redirects output to a file called nohup.out in the current directory. You can check on it later:

$ tail -f nohup.out         # Watch the output in real time
Processing batch 1 of 50...
Processing batch 2 of 50...
Processing batch 3 of 50...

Redirect nohup output to a custom file

$ nohup ./backup.sh > /var/log/backup.log 2>&1 &
[1] 4350

The nohup + & pattern

Almost always, you combine nohup with &:

  • nohup alone — Protects from SIGHUP but still runs in the foreground.
  • & alone — Runs in background but the process dies if you close the terminal.
  • nohup ... & — Both: runs in the background AND survives terminal close.
$ nohup python3 data_pipeline.py > pipeline.log 2>&1 &
[1] 4400
$ exit                      # Safe to log out; the script keeps running

# Check later if it is still running
$ pgrep -a data_pipeline
4400 python3 data_pipeline.py

14. nice / renice — Process Priority

Every process has a nice value that influences how much CPU time the scheduler gives it. The name "nice" comes from the idea that a "nicer" process yields more CPU to others.

  • Nice values range from -20 (highest priority, least nice) to 19 (lowest priority, most nice).
  • The default nice value is 0.
  • Only root (or sudo) can set negative nice values (higher priority).
  • Regular users can only make their processes nicer (higher nice value, lower priority).
  Priority Scale:
  -20 ........... 0 ........... 19
   ^               ^               ^
   |               |               |
  Highest        Default         Lowest
  priority       priority        priority
  (greedy)       (normal)        (generous)
  Root only      Anyone          Anyone

nice — start a process with a specific priority

$ nice -n 10 tar czf backup.tar.gz /home/alice/
# Runs tar at nice 10 (low priority, won't slow down other work)

$ nice -n 19 find / -name "*.tmp" -delete
# Lowest priority: runs only when CPU is idle

$ sudo nice -n -10 /opt/critical-app/start.sh
# High priority (needs root): gets more CPU time than normal processes

renice — change priority of a running process

$ renice 15 -p 3201         # Set PID 3201 to nice 15
3201 (process ID) old priority 0, new priority 15

$ sudo renice -5 -p 998     # Root can increase priority (negative nice)
998 (process ID) old priority 0, new priority -5

$ renice 10 -u alice        # Set all of alice's processes to nice 10

$ ps -eo pid,ni,comm | head -5    # Check nice values
  PID  NI COMMAND
    1   0 systemd
    2   0 kthreadd
  312   0 systemd-journal
 3201  15 firefox
When to use nice / renice

Use nice for long-running, resource-heavy tasks that you do not want to slow down interactive work. Examples: backups, file compression, data processing scripts, large compiles. This way, the task takes CPU when available but steps aside when the system is busy with more important work.

Exercise 1: Process Detective

Complete these tasks in order:

  1. Open three terminal windows and run sleep 1000 in two of them.
  2. In the third terminal, use ps aux | grep sleep to find the sleep processes.
  3. Use pgrep -a sleep to find them more cleanly.
  4. Send SIGTERM to one of them with kill.
  5. Send SIGKILL to the other with kill -9.
  6. Verify both are gone with pgrep sleep.
Show solution 
# Terminal 1:
$ sleep 1000

# Terminal 2:
$ sleep 1000

# Terminal 3:
$ pgrep -a sleep
5001 sleep 1000
5002 sleep 1000
$ kill 5001               # Graceful termination
$ kill -9 5002            # Force kill
$ pgrep sleep             # No output = both are gone
Exercise 2: Job Control Workflow

Practice the full job control workflow:

  1. Run sleep 500 & to start a background job.
  2. Run sleep 600 (foreground), then press Ctrl+Z to suspend it.
  3. Run jobs to see both jobs.
  4. Use bg %2 to resume the second job in the background.
  5. Use fg %1 to bring the first job to the foreground.
  6. Press Ctrl+C to kill it.
  7. Use kill %2 to terminate the remaining job.
  8. Run jobs to confirm no jobs remain.
Show solution 
$ sleep 500 &
[1] 5100
$ sleep 600
^Z
[2]+  Stopped                 sleep 600
$ jobs
[1]-  Running                 sleep 500 &
[2]+  Stopped                 sleep 600
$ bg %2
[2]+ sleep 600 &
$ fg %1
sleep 500
^C
$ kill %2
[2]+  Terminated              sleep 600
$ jobs
# No output = no jobs left
Exercise 3: Surviving Logout with nohup

Test that nohup keeps a process alive:

  1. In a terminal, run: nohup sleep 300 &
  2. Check the PID: pgrep -a sleep
  3. Close the terminal window completely.
  4. Open a new terminal and run pgrep -a sleep — the process should still be running.
  5. Clean up: pkill -f "sleep 300"
Show solution 
$ nohup sleep 300 &
[1] 5200
nohup: ignoring input and appending output to 'nohup.out'
$ pgrep -a sleep
5200 sleep 300
# Close this terminal, open a new one:
$ pgrep -a sleep
5200 sleep 300             # Still running!
$ pkill -f "sleep 300"     # Clean up

Quizzes

Quiz 1: Signals and Processes
  1. What is the default signal sent by kill PID?
  2. Which signal cannot be caught or ignored by a process?
  3. What does SIGHUP do when sent to many daemon processes?
  4. What keyboard shortcut sends SIGINT to a foreground process?
  5. What is a zombie process, and is it harmful?
Show answers
  1. SIGTERM (signal 15) — a polite request to terminate.
  2. SIGKILL (signal 9) and SIGSTOP (signal 19) cannot be caught or ignored.
  3. Many daemons (like nginx, apache, sshd) reload their configuration when they receive SIGHUP, rather than terminating.
  4. Ctrl+C sends SIGINT (signal 2) to the foreground process.
  5. A zombie is a process that has finished executing but whose parent has not yet read its exit status. A few zombies are normal and harmless. Many zombies indicate a buggy parent process that is not properly reaping its children.
Quiz 2: Job Control and Background Processes
  1. What is the difference between command & and nohup command &?
  2. How do you suspend a running foreground process?
  3. After suspending a process, how do you resume it in the background?
  4. What does the + sign mean in the output of jobs?
  5. If you start a process with nice value 10 and want to change it to 5, what command do you use?
  6. Can a regular (non-root) user decrease the nice value (increase priority) of their process from 10 to 5?
Show answers
  1. command & runs in the background but dies when the terminal closes. nohup command & runs in the background AND survives terminal closure because it ignores SIGHUP.
  2. Press Ctrl+Z. This sends SIGTSTP (signal 20) which suspends the process.
  3. Use the bg command (or bg %N for a specific job number).
  4. The + marks the current (most recent) job — the one that fg and bg will act on by default.
  5. renice 5 -p PID (replace PID with the process ID).
  6. No. Regular users can only increase the nice value (lower priority). Decreasing the nice value (raising priority) requires root/sudo: sudo renice 5 -p PID.
