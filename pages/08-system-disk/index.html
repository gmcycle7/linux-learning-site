Chapter 8: System & Disk Information

Understanding your system is fundamental to administering Linux. This chapter covers commands that answer critical questions: How much disk space is left? How much memory is available? What hardware is installed? How long has the system been running? Whether you are troubleshooting a slow server, planning storage, or just getting oriented on an unfamiliar machine, these commands are essential.

What You Will Learn

By the end of this chapter you will be able to check disk space, memory usage, CPU information, system uptime, block devices, mounted filesystems, and user identity — all from the command line.

df — Disk Free Space

What it does: df (disk free) reports how much disk space is used and available on each mounted filesystem. It reads from the kernel's mount table, so it shows the perspective of the filesystem (not individual files).

Why it matters: When a disk fills up, services crash, logs stop writing, and databases corrupt. Checking df regularly is one of the most basic sysadmin habits.

Flags Reference

-hHuman-readable sizes (K, M, G)
-HHuman-readable using powers of 1000 (not 1024)
-TShow filesystem type (ext4, xfs, tmpfs, etc.)
-iShow inode usage instead of block usage
-aInclude pseudo-filesystems (proc, sysfs, etc.)
-x TYPEExclude a filesystem type
--totalAdd a grand total row at the bottom
--outputChoose specific columns to display

Common Mistake

df shows space from the filesystem's perspective. If you delete a large file but a process still has it open, df will not show the freed space until that process closes the file handle. Use lsof +L1 to find such deleted-but-open files.

du — Disk Usage

What it does: du (disk usage) calculates how much space files and directories actually consume. Unlike df which looks at the whole filesystem, du walks a directory tree and sums up individual file sizes.

Why it matters: When df says you are low on space, du is how you find which directories are the culprits.

df vs du — Why They Show Different Numbers

df and du often report different totals for the same filesystem. This is normal and expected:

Aspectdfdu
Data sourceFilesystem metadata (superblock)Walks directory tree, sums files
Deleted-but-open filesStill counted as usedNot counted (no directory entry)
Reserved blocksIncluded in the totalNot visible
Sparse filesReports actual disk blocksCan show apparent size with --apparent-size
SpeedInstant (reads metadata)Slow on large trees (walks every file)
Best for"How full is the disk?""Which directory is eating space?"

Mental Model: Disk Space vs Inodes

Mental Model: Disk Space vs Inodes

Think of a filesystem like a library. Disk space is the shelf space — how many pages of books you can physically store. Inodes are the catalog cards — each file gets one card regardless of how big the book is.

You can run out of either one independently:

  • Out of disk space: You have millions of large files filling the shelves. df -h shows 100% used.
  • Out of inodes: You have millions of tiny files (like a mail server creating one file per email). df -i shows 100% IUse%. There is plenty of shelf space, but no more catalog cards.

When you see "No space left on device" but df -h shows free space, check df -i — you may have run out of inodes.

free — Memory Usage

What it does: free displays the total amount of physical memory (RAM) and swap space, showing how much is used, free, and available.

Why it matters: Understanding memory usage is essential for diagnosing performance issues. A common misconception is that high "used" memory means you are running out — Linux intentionally uses free RAM for caching.

Flags Reference

FlagMeaning
-hHuman-readable (auto-selects K, M, G)
-mDisplay in megabytes
-gDisplay in gigabytes
-bDisplay in bytes
-s NRepeat every N seconds
-c NRepeat N times (use with -s)
-tShow a total line (RAM + swap)
-wWide output (separate buffers and cache columns)

Understanding the Output

              total        used        free      shared  buff/cache   available
Mem:           15Gi       5.2Gi       1.8Gi       256Mi       8.4Gi        9.5Gi
Swap:         2.0Gi       100Mi       1.9Gi
ColumnWhat It Means
totalTotal installed RAM
usedMemory actively used by processes
freeCompletely unused memory (not even cache)
sharedMemory used by tmpfs and shared between processes
buff/cacheMemory used for disk caching (reclaimable!)
availableMemory available for new processes (free + reclaimable cache). This is the number you should look at.

Key Insight

On a healthy Linux system, "free" memory is often very low because Linux uses unused RAM as disk cache. Look at the available column, not "free". If "available" is very low, then you should worry.

uptime — System Uptime & Load Averages

What it does: uptime shows how long the system has been running, how many users are logged in, and the system load averages.

Why it matters: Load averages are a quick health check for system performance. A sudden spike may indicate runaway processes or unexpected traffic.

Examples

$ uptime
 14:32:07 up 45 days,  3:22,  2 users,  load average: 0.52, 0.78, 0.65
$ uptime -p
up 45 days, 3 hours, 22 minutes
$ uptime -s
2026-02-14 11:10:05

The three load average numbers represent the average number of processes waiting for CPU time over the last 1 minute, 5 minutes, and 15 minutes.

Understanding Load Averages

Load average represents the average number of processes in a runnable or uninterruptible state. Think of it like a queue at a checkout counter:

  • On a single-core machine, load 1.0 means the CPU is fully utilized with no queue. Load 2.0 means one process is running and one is waiting.
  • On a 4-core machine, load 4.0 means all cores are busy. Load 2.0 means you still have headroom.

Rule of thumb: Divide load average by number of CPU cores. If the result is consistently above 1.0, the system is overloaded.

# Check number of cores to interpret load
$ nproc
4
# Load of 3.5 on 4 cores = 3.5/4 = 0.875 — healthy
# Load of 8.0 on 4 cores = 8.0/4 = 2.0 — overloaded!

The three numbers (1, 5, 15 minute averages) show the trend. If 1-minute is much higher than 15-minute, load is spiking right now. If 15-minute is high but 1-minute is low, a spike just ended.

$ cat /proc/uptime
3897732.45 15423897.22
# First number: seconds since boot. Second: cumulative idle seconds across all cores.
$ cat /proc/loadavg
0.52 0.78 0.65 2/345 12456
# load1 load5 load15 running/total last_pid
$ w

USER     TTY      FROM             LOGIN@   IDLE   JCPU   PCPU WHAT
alice    pts/0    192.168.1.10     10:05    3:22m  0.12s  0.04s vim app.py
bob      pts/1    192.168.1.20     14:30    0.00s  0.02s  0.00s w
$ uptime | awk -F'load average:' '{print $2}'

$ uptime | awk '{print $3, $4}'

Understanding Partitions and Mount Points

A disk (like sda) is the physical device. It is divided into partitions (like sda1, sda2). Each partition can contain a filesystem (ext4, xfs, etc.) and be mounted at a directory in the file tree.

Physical Disk (sda, 50G)
├── Partition 1 (sda1, 512M) → ext4 → mounted at /boot
├── Partition 2 (sda2, 48G)  → ext4 → mounted at /
└── Partition 3 (sda3, 1.5G) → swap → [SWAP]

Physical Disk (sdb, 100G)
└── Partition 1 (sdb1, 100G) → xfs  → mounted at /data

What it does: mount attaches a filesystem to a directory in the file tree. Without arguments, it lists all currently mounted filesystems.

Why it matters: Accessing USB drives, network shares, disk images, and additional partitions all require mounting. Understanding mounts is fundamental to Linux disk management.

Examples

Understanding /etc/fstab

/etc/fstab (file system table) defines which filesystems are mounted automatically at boot. Each line specifies a device, mount point, filesystem type, options, dump flag, and fsck order:

# /etc/fstab — device  mountpoint  type  options        dump  fsck
/dev/sda2       /           ext4  defaults           0     1
/dev/sda1       /boot       ext4  defaults           0     2
/dev/sdb1       /data       xfs   defaults,noatime   0     2
/dev/sda3       none        swap  sw                 0     0
UUID=a1b2c3d4   /backup     ext4  defaults,nofail    0     2

Using UUID= instead of /dev/sdX is safer because device names can change between boots, but UUIDs are permanent. Find UUIDs with lsblk -f or blkid.

Caution

Editing /etc/fstab incorrectly can make your system unbootable. Always test entries with sudo mount -a before rebooting. Use the nofail option for non-critical mounts so the system still boots if that device is absent.

lscpu — CPU Information

What it does: lscpu displays detailed information about the CPU architecture — number of cores, threads, model name, cache sizes, and virtualization support.

Why it matters: Knowing your CPU specs helps you understand performance limits, plan parallel workloads, and configure applications that depend on core counts.

Examples

$ lscpu
Architecture:          x86_64
CPU op-mode(s):        32-bit, 64-bit

whoami — Current User

What it does: whoami prints the username of the current effective user. That is it — one word, no flags (well, almost).

Why it matters: When you are in a script, when you have used su or sudo, or when you are ssh'ed into multiple machines, whoami quickly confirms who the system thinks you are.

Examples

$ whoami
alice
$ sudo whoami
root
$ su - bob -c "whoami"
bob
$ echo "Logged in as: $(whoami)"
Logged in as: alice
$ if [ "$(whoami)" != "root" ]; then echo "Run as root!"; fi
Run as root!
$ echo $USER
alice
# $USER is the login user. whoami is the effective user (may differ after sudo).
$ logname
alice
# logname shows the login name, even after su/sudo
$ who am i
alice    pts/0        2026-03-31 10:05 (192.168.1.10)
# Shows login user with terminal and source IP
Common Confusion
$ sudo su
# echo $USER
alice    # $USER still shows original login user!
# whoami
root     # whoami correctly shows effective user
Best Practice
# In scripts, use whoami or id for the effective user:
$ if [ "$(id -u)" -eq 0 ]; then
    echo "Running as root"
fi

id — User Identity

What it does: id prints the real and effective user ID (UID), group ID (GID), and all group memberships. It tells you everything about who you are from the system's perspective.

Why it matters: Permission errors often come down to UID/GID. When troubleshooting "permission denied" errors, id shows you exactly what groups you belong to and whether you have the access you need.

Flags Reference

FlagOutput
idFull info: uid, gid, groups
-uPrint only the effective UID
-gPrint only the effective GID
-GPrint all group IDs
-nPrint names instead of numbers (use with -u, -g, -G)
-rPrint real ID instead of effective ID

Examples

$ id
uid=1000(alice) gid=1000(alice) groups=1000(alice),4(adm),27(sudo),33(www-data),999(docker)
$ id -u
1000
$ id -un
alice
$ id -g
1000
$ id -gn
alice
$ id -Gn
alice adm sudo www-data docker
$ id bob
uid=1001(bob) gid=1001(bob) groups=1001(bob),27(sudo)
$ id root
uid=0(root) gid=0(root) groups=0(root)
$ groups
alice adm sudo www-data docker
# Shortcut for id -Gn
$ id -u bob
1001
UID 0 = Root

The root user always has UID 0. In scripts, checking id -u is more reliable than checking whoami because the root account could be renamed (though that is extremely rare).

Exercise 2: System Snapshot

Write a one-liner (or short script) that produces a quick system report including:

  • Hostname and kernel version
  • CPU model and core count
  • Total and available memory
  • Uptime and load average
  • Disk usage summary
Show Solution 
$ echo "=== System Report ===" && \
  echo "Host: $(hostname) | Kernel: $(uname -r)" && \
  echo "CPU: $(lscpu | grep 'Model name' | sed 's/.*: *//')" && \
  echo "Cores: $(nproc)" && \
  echo "Memory: $(free -h | awk '/Mem:/ {print "Total: "$2" | Available: "$7}')" && \
  echo "Uptime: $(uptime -p)" && \
  echo "Load: $(cat /proc/loadavg | awk '{print $1, $2, $3}')" && \
  echo "=== Disk ===" && \
  df -h --total | grep -E '(Filesystem|total)'

Knowledge Check

1. Your server shows "No space left on device" but df -h shows 30% used. What should you check next?
B. Check inode usage with df -i. If the filesystem has run out of inodes (even though there is free space), no new files can be created. This happens when millions of tiny files consume all available inodes.
2. A 4-core server shows load average: 6.00, 4.50, 2.00. What does this tell you?
C. The load averages go 2.00 (15 min) → 4.50 (5 min) → 6.00 (1 min), which means load is increasing. The 1-minute average of 6.00 divided by 4 cores = 1.5, meaning processes are queuing up. Something recent is causing a spike and it has not stopped yet.
