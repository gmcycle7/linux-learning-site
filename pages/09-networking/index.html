Chapter 9: Networking Basics

Nearly everything in modern computing involves a network. Whether you are SSHing into a remote server, downloading files, debugging a web app, or checking if a service is reachable, you need networking commands. This chapter covers the essential tools for inspecting network configuration, testing connectivity, transferring data, querying DNS, and connecting to remote machines.

What You Will Learn

IP address management, connectivity testing, socket inspection, HTTP requests, file downloads, DNS queries, route tracing, and remote access via SSH/SCP/rsync.

Mental Model: How Networking Works

Mental Model: How Networking Works

Before diving into commands, understand these three core concepts:

IP Addresses — Every device on a network has a unique address. Think of it like a postal address for your computer. IPv4 looks like 192.168.1.10, IPv6 like fe80::1.

Ports — A single IP address can run many services. Ports are like apartment numbers at the same street address. SSH uses port 22, HTTP uses port 80, HTTPS uses port 443. Ports range from 0-65535.

DNS — The Domain Name System translates human-readable names (like example.com) into IP addresses (like 93.184.216.34). Your computer asks a DNS server "What is the IP for example.com?" before it can connect.

You type: https://example.com/page
         |
         v
[DNS Lookup] "What IP is example.com?"
         |
         v
DNS says: 93.184.216.34
         |
         v
[TCP Connection] Connect to 93.184.216.34 on port 443
         |
         v
[HTTP Request] GET /page
         |
         v
[Response] HTML content returned to your browser

ip — Network Interface & Routing

What it does: The ip command is the modern replacement for ifconfig, route, and arp. It manages and displays network interfaces, IP addresses, and routing tables.

Why it matters: ifconfig is deprecated on most modern distributions. The ip command is more powerful, consistent, and is the standard tool for network configuration.

Examples

$ ip addr show
# (or shorthand: ip a)
1: lo: <LOOPBACK,UP,LOWER_UP> mtu 65536
    link/loopback 00:00:00:00:00:00 brd 00:00:00:00:00:00
    inet 127.0.0.1/8 scope host lo
    inet6 ::1/128 scope host
2: eth0: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500
    link/ether 52:54:00:ab:cd:ef brd ff:ff:ff:ff:ff:ff
    inet 192.168.1.10/24 brd 192.168.1.255 scope global eth0
    inet6 fe80::5054:ff:feab:cdef/64 scope link
$ ip addr show eth0
# Show only a specific interface
$ ip -4 addr
# Show only IPv4 addresses
$ ip link show
# Show link-layer info (MAC addresses, state)
1: lo: <LOOPBACK,UP,LOWER_UP> mtu 65536 state UNKNOWN
    link/loopback 00:00:00:00:00:00 brd 00:00:00:00:00:00
2: eth0: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 state UP
    link/ether 52:54:00:ab:cd:ef brd ff:ff:ff:ff:ff:ff
$ sudo ip link set eth0 down
# Disable a network interface
$ sudo ip link set eth0 up
# Enable a network interface
$ ip route show
# (or shorthand: ip r)
default via 192.168.1.1 dev eth0 proto dhcp metric 100
192.168.1.0/24 dev eth0 proto kernel scope link src 192.168.1.10 metric 100
$ ip route get 8.8.8.8
8.8.8.8 via 192.168.1.1 dev eth0 src 192.168.1.10 uid 1000
# Shows which route/interface would be used to reach that IP
$ ip -br addr
# Brief format — clean summary
lo               UNKNOWN        127.0.0.1/8 ::1/128
eth0             UP             192.168.1.10/24 fe80::5054:ff:feab:cdef/64
$ ip neigh show
# Show ARP table (neighbors)
192.168.1.1 dev eth0 lladdr 00:11:22:33:44:55 REACHABLE
192.168.1.20 dev eth0 lladdr aa:bb:cc:dd:ee:ff STALE
$ ip -s link show eth0
# Show interface statistics (packets, bytes, errors)
ifconfig is Deprecated

ifconfig still works on many systems but it is part of the net-tools package which is no longer installed by default. Use ip instead. Mapping: ifconfig → ip addr, route → ip route, arp → ip neigh.

ping — Test Connectivity

What it does: ping sends ICMP echo request packets to a host and reports if it responds. It is the first tool you reach for when testing "Can I reach this machine?"

Why it matters: Ping is the most basic network diagnostic. If ping fails, there is either a DNS problem, a routing problem, a firewall blocking ICMP, or the host is down.

Examples

$ ping google.com
PING google.com (142.250.80.46) 56(84) bytes of data.
64 bytes from lax17s55-in-f14.1e100.net (142.250.80.46): icmp_seq=1 ttl=118 time=11.2 ms
64 bytes from lax17s55-in-f14.1e100.net (142.250.80.46): icmp_seq=2 ttl=118 time=10.8 ms
64 bytes from lax17s55-in-f14.1e100.net (142.250.80.46): icmp_seq=3 ttl=118 time=11.0 ms
^C
--- google.com ping statistics ---
3 packets transmitted, 3 received, 0% packet loss, time 2003ms
rtt min/avg/max/mdev = 10.8/11.0/11.2/0.163 ms
$ ping -c 4 google.com
# Send exactly 4 packets and stop
$ ping -c 3 -W 2 192.168.1.100
# 3 packets, 2-second timeout per packet
$ ping -i 0.2 -c 10 google.com
# Send packets every 0.2 seconds (faster ping, needs root for <0.2)
$ ping -q -c 10 google.com
# Quiet mode — only show summary
--- google.com ping statistics ---
10 packets transmitted, 10 received, 0% packet loss, time 9012ms
rtt min/avg/max/mdev = 10.5/11.1/12.3/0.521 ms
$ ping -s 1000 -c 3 google.com
# Send larger packets (1000 bytes instead of default 56)
$ ping -4 google.com
# Force IPv4
$ ping -6 google.com
# Force IPv6

Understanding the output:

FieldMeaning
icmp_seqPacket sequence number (gaps = lost packets)
ttlTime to live (hops remaining). Low TTL = far away host.
timeRound-trip time in milliseconds. Under 50ms is good for most connections.
packet lossPercentage of packets that got no reply. 0% is ideal.
No response does not always mean the host is down

Many servers and firewalls block ICMP (ping) traffic for security. A host that does not respond to ping may still be reachable on other ports. Try curl or ssh instead.

ss — Socket Statistics

What it does: ss (socket statistics) displays information about network sockets — which ports are listening, which connections are established, and which processes own them.

Why it matters: When debugging connectivity issues ("Why can I not connect to port 8080?"), ss shows you if anything is actually listening there.

Flags Reference

FlagMeaning
-tTCP sockets only
-uUDP sockets only
-lListening sockets only
-nDo not resolve service names (show port numbers)
-pShow process using the socket
-aAll sockets (listening + established)
-4IPv4 only
-6IPv6 only
-sSummary statistics

Examples

$ ss -tlnp
# TCP, listening, numeric, with process names — the most common usage
State   Recv-Q  Send-Q  Local Address:Port   Peer Address:Port  Process
LISTEN  0       128     0.0.0.0:22            0.0.0.0:*          users:(("sshd",pid=1234,fd=3))
LISTEN  0       511     0.0.0.0:80            0.0.0.0:*          users:(("nginx",pid=5678,fd=6))
LISTEN  0       128     127.0.0.1:3306        0.0.0.0:*          users:(("mysqld",pid=9012,fd=22))
LISTEN  0       128     0.0.0.0:443           0.0.0.0:*          users:(("nginx",pid=5678,fd=7))
$ ss -tunap
# TCP and UDP, all sockets, numeric, with process
$ ss -t state established
# Show only established TCP connections
Recv-Q  Send-Q  Local Address:Port   Peer Address:Port
0       0       192.168.1.10:22      192.168.1.20:54321
0       0       192.168.1.10:80      203.0.113.50:12345
$ ss -tlnp | grep :80
# Check if anything is listening on port 80
LISTEN  0  511  0.0.0.0:80  0.0.0.0:*  users:(("nginx",pid=5678,fd=6))
$ ss -s
# Summary of socket types
Total: 234
TCP:   45 (estab 12, closed 5, orphaned 0, timewait 3)
UDP:   8
...
$ ss -t -o
# Show timer information
$ ss dst 192.168.1.20
# Show connections to a specific destination
$ ss sport = :22
# Show connections from source port 22
Memory Aid: ss -tulnp

The most commonly used ss invocation is ss -tulnp (TCP + UDP, listening, numeric, processes). Remember it as "TULNP" or "tulip" minus the i.

netstat — Legacy Socket Statistics

What it does: netstat is the older tool for displaying network connections, routing tables, and interface statistics. It does the same things as ss but is slower and part of the deprecated net-tools package.

Why you still see it: Many guides, scripts, and interview questions still reference netstat. Know the equivalents:

Tasknetstat (legacy)ss (modern)
Listening TCP portsnetstat -tlnpss -tlnp
All connectionsnetstat -anpss -anp
Routing tablenetstat -rnip route
Interface statsnetstat -iip -s link
Socket summarynetstat -sss -s

Examples

$ netstat -tlnp
Proto Recv-Q Send-Q Local Address    Foreign Address  State   PID/Program name
tcp        0      0 0.0.0.0:22       0.0.0.0:*        LISTEN  1234/sshd
tcp        0      0 0.0.0.0:80       0.0.0.0:*        LISTEN  5678/nginx
tcp        0      0 127.0.0.1:3306   0.0.0.0:*        LISTEN  9012/mysqld
$ netstat -an | grep ESTABLISHED | wc -l
12
# Count active connections
$ netstat -rn
# Routing table
Destination     Gateway         Genmask         Flags Metric Ref Use Iface
0.0.0.0         192.168.1.1     0.0.0.0         UG    100    0   0   eth0
192.168.1.0     0.0.0.0         255.255.255.0   U     100    0   0   eth0
$ netstat -i
# Interface statistics
$ netstat -tunap
# All TCP/UDP sockets with process info
$ netstat -tlnp | grep :443
# Check who is listening on HTTPS port
$ netstat -s
# Protocol statistics (detailed counters)
$ netstat -anp | grep nginx
# All sockets related to nginx
Prefer ss over netstat

ss is faster, more feature-rich, and installed by default on modern distributions. Use netstat only when ss is not available or when maintaining legacy scripts.

curl — Transfer URLs

What it does: curl (Client URL) transfers data to or from a server using supported protocols (HTTP, HTTPS, FTP, and many more). It is an incredibly versatile tool for testing APIs, downloading files, and debugging web services.

Why it matters: If you work with web services, APIs, or need to test HTTP responses from the command line, curl is indispensable.

Flags Reference

FlagMeaning
-o FILESave output to a specific file
-OSave with the remote filename
-IFetch headers only (HEAD request)
-X METHODSpecify HTTP method (GET, POST, PUT, DELETE)
-d DATASend data in POST request body
-H HEADERAdd a custom header
-vVerbose output (shows full request/response)
-sSilent mode (no progress bar)
-LFollow redirects
-u USER:PASSHTTP authentication
-kSkip SSL certificate verification (insecure)
-w FORMATCustom output format (timing, status codes, etc.)

Examples

$ curl https://example.com
# Fetch a web page and print to stdout
$ curl -o page.html https://example.com
# Save to a specific file
$ curl -O https://example.com/file.tar.gz
# Save with the remote filename (file.tar.gz)
$ curl -I https://example.com
HTTP/2 200
content-type: text/html; charset=UTF-8
content-length: 1256
date: Mon, 31 Mar 2026 14:32:10 GMT
server: ECAcc (lax/1234)
$ curl -X POST -H "Content-Type: application/json" \
  -d '{"name":"Alice","email":"alice@example.com"}' \
  https://api.example.com/users
# POST JSON data to an API
$ curl -X PUT -H "Authorization: Bearer TOKEN123" \
  -d '{"status":"active"}' \
  https://api.example.com/users/42
# PUT request with auth header
$ curl -s https://api.example.com/data | jq .
# Silent mode piped to jq for pretty JSON formatting
$ curl -v https://example.com 2>&1 | head -30
# Verbose output shows TLS handshake, headers, everything
$ curl -L http://example.com/redirect
# Follow HTTP redirects (301, 302)
$ curl -w "HTTP Code: %{http_code}\nTime: %{time_total}s\n" -o /dev/null -s https://example.com
HTTP Code: 200
Time: 0.234s
$ curl -X DELETE https://api.example.com/users/42
# DELETE request
$ curl -d "username=alice&password=secret" https://example.com/login
# POST form data (application/x-www-form-urlencoded)
Security Warning

Never use curl -k in production. It disables SSL certificate verification, making you vulnerable to man-in-the-middle attacks. Use it only for testing with self-signed certificates.

wget — Download Files

What it does: wget (Web Get) downloads files from the web. It is designed specifically for downloading and supports recursive downloads, retries, and resuming interrupted downloads.

Why it matters: When you need to download files on a server that has no GUI (no browser), wget is the go-to tool. It handles retries and interrupted connections gracefully.

Examples

$ wget https://example.com/file.tar.gz
# Download a file (saves to current directory)
--2026-03-31 14:32:10--  https://example.com/file.tar.gz
Resolving example.com... 93.184.216.34
Connecting to example.com|93.184.216.34|:443... connected.
HTTP request sent, awaiting response... 200 OK
Length: 52428800 (50M) [application/gzip]
Saving to: 'file.tar.gz'

file.tar.gz         100%[===================>]  50.00M  12.5MB/s    in 4.0s

2026-03-31 14:32:14 (12.5 MB/s) - 'file.tar.gz' saved [52428800/52428800]
$ wget -O custom-name.tar.gz https://example.com/file.tar.gz
# Save with a custom filename
$ wget -c https://example.com/bigfile.iso
# Resume a partially downloaded file
$ wget -q https://example.com/file.tar.gz
# Quiet mode (no progress output)
$ wget -r -l 2 -np https://example.com/docs/
# Recursive download, 2 levels deep, no parent directories
$ wget -i urls.txt
# Download all URLs listed in a file
$ wget --limit-rate=1m https://example.com/bigfile.iso
# Limit download speed to 1 MB/s
$ wget -b https://example.com/bigfile.iso
# Download in background (logs to wget-log)
$ wget --mirror --convert-links --adjust-extension --page-requisites https://example.com/
# Mirror an entire website for offline viewing
$ wget --spider https://example.com/file.tar.gz
# Check if a file exists without downloading (dry run)

Rule of Thumb

Use curl when working with APIs, testing endpoints, or sending custom HTTP requests. Use wget when downloading files, especially large ones or entire directories.

nslookup — DNS Lookup

What it does: nslookup queries DNS servers to find the IP address associated with a domain name (or vice versa).

Why it matters: When a website is unreachable, the first question is: "Is DNS resolving correctly?" nslookup answers that quickly.

Examples

$ nslookup example.com
Server:		127.0.0.53
Address:	127.0.0.53#53

Non-authoritative answer:
Name:	example.com
Address: 93.184.216.34
$ nslookup -type=MX example.com
# Look up mail exchange records
example.com	mail exchanger = 10 mail.example.com.
$ nslookup -type=NS example.com
# Look up nameservers
example.com	nameserver = a.iana-servers.net.
example.com	nameserver = b.iana-servers.net.
$ nslookup example.com 8.8.8.8
# Query a specific DNS server (Google's)
$ nslookup -type=TXT example.com
# Look up TXT records (SPF, DKIM, etc.)
$ nslookup 93.184.216.34
# Reverse lookup: IP to hostname
34.216.184.93.in-addr.arpa	name = example.com.
$ nslookup -type=AAAA example.com
# Look up IPv6 address
$ nslookup -type=SOA example.com
# Look up Start of Authority record

dig — DNS Query Tool

What it does: dig (Domain Information Groper) performs DNS lookups and displays detailed results including TTL, query time, and authority information. It is more powerful and scriptable than nslookup.

Why it matters: For serious DNS troubleshooting, dig gives you more information and control than nslookup.

Examples

$ dig example.com
; <<>> DiG 9.18.12 <<>> example.com
;; ANSWER SECTION:
example.com.		86400	IN	A	93.184.216.34

;; Query time: 23 msec
;; SERVER: 127.0.0.53#53(127.0.0.53)
;; WHEN: Mon Mar 31 14:32:10 UTC 2026
;; MSG SIZE  rcvd: 56
$ dig +short example.com
93.184.216.34
# Just the answer, nothing else
$ dig MX example.com
# Query MX records
$ dig @8.8.8.8 example.com
# Query a specific DNS server
$ dig -x 93.184.216.34
# Reverse DNS lookup
$ dig +trace example.com
# Trace the full DNS delegation chain from root servers
$ dig example.com ANY
# Request all record types
$ dig +short example.com NS
a.iana-servers.net.
b.iana-servers.net.
$ dig +noall +answer example.com
# Show only the answer section (clean output)
example.com.		86400	IN	A	93.184.216.34
$ dig +stats example.com | grep "Query time"
;; Query time: 23 msec

traceroute — Trace Network Path

What it does: traceroute shows the path packets take from your machine to a destination, listing every router (hop) along the way and the time at each hop.

Why it matters: When connectivity is slow or failing, traceroute shows you where the problem is — is it your local network, your ISP, or a router in between?

Examples

$ traceroute google.com
traceroute to google.com (142.250.80.46), 30 hops max, 60 byte packets
 1  gateway (192.168.1.1)  1.234 ms  1.123 ms  1.098 ms
 2  isp-router (10.0.0.1)  5.432 ms  5.321 ms  5.234 ms
 3  core-router.isp.net (203.0.113.1)  12.345 ms  12.234 ms  12.123 ms
 4  * * *
 5  lax-edge.google.com (72.14.237.1)  11.234 ms  11.123 ms  11.098 ms
 6  lax17s55-in-f14.1e100.net (142.250.80.46)  11.456 ms  11.345 ms  11.234 ms
$ traceroute -n google.com
# Numeric only (skip DNS lookups for faster output)
$ traceroute -m 15 google.com
# Max 15 hops instead of default 30
$ traceroute -w 2 google.com
# Wait 2 seconds per probe (default is 5)
$ traceroute -I google.com
# Use ICMP instead of UDP (may work better through firewalls)
$ traceroute -T -p 443 google.com
# Use TCP on port 443 (useful when ICMP/UDP is blocked)
$ tracepath google.com
# Simpler alternative that doesn't need root
$ mtr google.com
# Combines ping + traceroute in a live updating display

Reading the output: Each numbered line is a "hop" (router). Three time values are shown (three probes). * * * means that router did not respond — this is common and does not necessarily indicate a problem. If all hops after a certain point are *, the destination is unreachable.

ssh — Secure Shell

What it does: ssh (Secure Shell) opens an encrypted connection to a remote machine, giving you a command-line session as if you were sitting at that machine.

Why it matters: SSH is the primary way to manage remote Linux servers. Every sysadmin, developer, and DevOps engineer uses it daily.

Examples

$ ssh alice@192.168.1.20
# Connect as user "alice" to IP 192.168.1.20
$ ssh alice@webserver.example.com
# Connect using a hostname
$ ssh -p 2222 alice@server.com
# Connect on a non-standard port
$ ssh alice@server.com "uptime && df -h"
# Run a command remotely without opening an interactive shell
 14:32:07 up 45 days,  3:22,  1 user,  load average: 0.52, 0.78, 0.65
Filesystem      Size  Used Avail Use% Mounted on
/dev/sda1        50G   12G   35G  26% /
$ ssh -v alice@server.com
# Verbose mode (debug connection issues)
$ ssh -L 8080:localhost:80 alice@server.com
# Local port forwarding: access server's port 80 via your localhost:8080
$ ssh -N -L 3307:localhost:3306 alice@server.com
# Forward MySQL port without opening a shell (-N = no command)
$ ssh -J jumphost.com alice@internal-server.com
# Jump through a bastion/jump host

SSH Key-Based Authentication

SSH Key Authentication

Instead of typing a password every time, you can use a key pair (public + private). The private key stays on your machine. The public key is placed on the server. This is more secure and more convenient.

YOUR MACHINE                          REMOTE SERVER
+------------------+                  +------------------+
| ~/.ssh/id_ed25519 |  --- proves --> | ~/.ssh/           |
| (private key)     |     identity    |   authorized_keys |
| NEVER share this  |                 |   (public key)    |
+------------------+                  +------------------+

Step 1: ssh-keygen (creates the key pair on your machine)
Step 2: ssh-copy-id user@server (copies public key to server)
Step 3: ssh user@server (logs in without a password)
$ ssh-keygen -t ed25519 -C "alice@work"
Generating public/private ed25519 key pair.
Enter file in which to save the key (/home/alice/.ssh/id_ed25519):
Enter passphrase (empty for no passphrase):
Your identification has been saved in /home/alice/.ssh/id_ed25519
Your public key has been saved in /home/alice/.ssh/id_ed25519.pub
$ ssh-copy-id alice@server.com
# Copies your public key to the server's authorized_keys
$ cat ~/.ssh/config
Host webserver
    HostName 192.168.1.20
    User alice
    Port 2222
    IdentityFile ~/.ssh/id_ed25519

Host dbserver
    HostName 10.0.1.50
    User admin
    ProxyJump webserver

$ ssh webserver
# Now you can just type "ssh webserver" instead of the full command
Never Share Your Private Key

Your private key (~/.ssh/id_ed25519) must never be shared, emailed, or committed to a repository. Only the public key (~/.ssh/id_ed25519.pub) is placed on servers.

scp — Secure Copy

What it does: scp (Secure Copy Protocol) copies files between your local machine and a remote machine over an encrypted SSH connection.

Why it matters: Need to copy a config file to a server or download a log file? scp is the simplest way to transfer files over SSH.

Examples

$ scp file.txt alice@server.com:/home/alice/
# Copy local file to remote server
$ scp alice@server.com:/var/log/app.log ./
# Copy remote file to current local directory
$ scp -r project/ alice@server.com:/home/alice/
# Copy an entire directory recursively
$ scp -P 2222 file.txt alice@server.com:/tmp/
# Use a non-standard SSH port (note: uppercase -P for scp)
$ scp alice@server1.com:/data/file.txt bob@server2.com:/backup/
# Copy between two remote servers (through your machine)
$ scp -C largefile.tar.gz alice@server.com:/data/
# Enable compression during transfer
$ scp -i ~/.ssh/mykey.pem file.txt alice@server.com:/tmp/
# Use a specific SSH key
$ scp *.log alice@server.com:/backup/logs/
# Copy multiple files matching a pattern
scp Syntax Pattern

The pattern is always scp [source] [destination]. Remote paths use the format user@host:/path. If either source or destination is local, just use the normal file path.

rsync — Efficient Sync

What it does: rsync synchronizes files and directories between two locations (local or remote). Unlike scp, it only transfers the differences between source and destination, making it extremely efficient for repeated transfers.

Why it matters: rsync is the standard tool for backups, deployments, and keeping directories in sync. It is faster than scp for everything except the first transfer.

Flags Reference

FlagMeaning
-aArchive mode (preserves permissions, timestamps, symlinks, recursive)
-vVerbose output
-zCompress data during transfer
-hHuman-readable numbers
--deleteDelete files in destination that do not exist in source
--dry-runShow what would be done without actually doing it
-nShort for --dry-run
--progressShow transfer progress
--excludeExclude files matching a pattern
-eSpecify the remote shell (e.g., -e "ssh -p 2222")
-PEquivalent to --partial --progress (resume + progress)

Examples

$ rsync -av /home/alice/project/ /backup/project/
# Sync a local directory to another local directory
$ rsync -avz /home/alice/project/ alice@server.com:/home/alice/project/
# Sync local to remote with compression
$ rsync -avz alice@server.com:/var/log/ ./server-logs/
# Sync remote to local
$ rsync -avz --delete /home/alice/project/ /backup/project/
# Mirror: sync AND delete files in destination that are not in source
$ rsync -avzn --delete /home/alice/project/ /backup/project/
# Dry run — see what WOULD happen without doing it
sending incremental file list
deleting old-file.txt
new-file.txt
modified-file.txt

sent 234 bytes  received 45 bytes  558.00 bytes/sec
total size is 12,345  speedup is 44.23 (DRY RUN)
$ rsync -avz --exclude='*.log' --exclude='.git/' src/ dest/
# Exclude log files and .git directory
$ rsync -avz -e "ssh -p 2222" /data/ alice@server.com:/data/
# Use a non-standard SSH port
$ rsync -avzP largefile.iso alice@server.com:/data/
# Show progress and allow resume of interrupted transfer
$ rsync -avz --include='*.jpg' --exclude='*' photos/ alice@server.com:/photos/
# Only sync .jpg files
$ rsync -avz --max-size='100M' /data/ /backup/
# Skip files larger than 100MB
$ rsync -avz --bwlimit=5000 /data/ alice@server.com:/data/
# Limit bandwidth to 5000 KB/s
Trailing Slash Matters!

With rsync, a trailing / on the source means "the contents of this directory." Without it, the directory itself is copied.

$ rsync -av project/ /backup/
# Copies CONTENTS of project/ into /backup/

$ rsync -av project /backup/
# Copies the project DIRECTORY into /backup/project/
Dangerous
$ rsync -avz --delete /wrong/source/ /important/data/
# If source is wrong/empty, --delete will ERASE your data!
Safe Approach
$ rsync -avzn --delete /source/ /dest/
# Always --dry-run first when using --delete
$ rsync -avz --delete /source/ /dest/
# Then run for real after verifying

Exercise 1: Network Reconnaissance

Perform the following tasks on your local machine:

  1. Find your IP address using ip addr. Identify the interface name and IP.
  2. Find your default gateway using ip route.
  3. Ping your default gateway — do you get a response?
  4. Use dig +short to look up the IP of google.com.
  5. Use ss -tlnp to list all services listening on your machine.
  6. Use traceroute (or tracepath) to see the hops to google.com.
Show Solution 
# 1. Find your IP
$ ip -br addr
# Look for the interface that is UP with an IP (not 127.0.0.1)

# 2. Default gateway
$ ip route | grep default
default via 192.168.1.1 dev eth0

# 3. Ping gateway
$ ping -c 3 192.168.1.1

# 4. DNS lookup
$ dig +short google.com

# 5. Listening services
$ sudo ss -tlnp

# 6. Traceroute
$ traceroute google.com
# or if not installed:
$ tracepath google.com

Knowledge Check

1. You need to check which process is listening on port 8080. Which command would you use?
B. ss -tlnp | grep :8080 shows which process is listening on TCP port 8080. The -p flag displays the process name and PID. Option C would connect to port 8080 but would not tell you which process is listening there.
2. What is the difference between rsync -av src/ dest/ and rsync -av src dest/?
B. The trailing slash on the source directory matters. src/ means "the contents of src" while src means "the src directory itself." With the trailing slash, files end up directly in dest/. Without it, they end up in dest/src/.
