Dangerous Commands and How to Stay Safe

Critical Warning

The commands on this page can permanently destroy data, corrupt your system, or make it completely unbootable. They are listed here so that you can recognize them and avoid running them by accident. Never run any of these commands on a real system unless you fully understand the consequences.

Linux gives you enormous power. Unlike Windows or macOS, there are very few guardrails preventing you from destroying your own system. The root user (and anyone using sudo) can do absolutely anything, including wiping the entire filesystem in a single command. This page documents the most dangerous commands and patterns, explains exactly what they do, and provides safe alternatives and protective habits.

Why learn dangerous commands?

You are not learning these to use them. You are learning these to recognize them. Malicious users sometimes post these commands in forums disguised as "helpful advice." Knowing what they do will keep you safe.

1. rm -rf / and rm -rf *

EXTREME DANGER: Total Data Destruction

This is the single most destructive command in Linux. It permanently deletes everything on your system with no recovery possible.

What it does

The rm command removes files. The flags change its behavior dramatically:

  • -r (recursive) — delete directories and all their contents, descending into every subdirectory
  • -f (force) — never prompt for confirmation, ignore non-existent files, override write protection
  • / — the root of the entire filesystem (everything on your computer)
# DO NOT RUN THIS - Deletes EVERYTHING on the system
$ sudo rm -rf /

# Also extremely dangerous - deletes everything in current directory
$ rm -rf *

# Hidden variation with space before slash - deletes current dir AND root
$ rm -rf / tmp/junk

Why it is catastrophic

This command deletes every file, every program, the kernel, the bootloader, all user data, all configurations — everything. The system will crash partway through as essential files are removed. Recovery requires a full reinstall from backup. If you have no backup, your data is gone forever.

Watch out for accidental spaces

rm -rf / tmp/junk (with a space after /) is very different from rm -rf /tmp/junk. The first command deletes the root filesystem AND a directory called tmp/junk. One misplaced space can destroy your system.

Safe alternatives and protection

  • Modern Linux distributions include the --preserve-root flag by default, which prevents rm -rf /. However, --no-preserve-root overrides it, and rm -rf /* bypasses it entirely.
  • Always use rm -ri (interactive) to confirm each deletion.
  • Install trash-cli and use trash-put instead of rm. Files go to a trash folder you can recover from.
  • Use ls first to see what would be deleted before running rm.
  • Set an alias: alias rm='rm -i' to always prompt for confirmation.
# SAFE: Check what you are about to delete first
$ ls /tmp/junk
file1.txt  file2.log  old_data/

# SAFE: Use interactive mode
$ rm -ri /tmp/junk
rm: descend into '/tmp/junk'? y
rm: remove regular file '/tmp/junk/file1.txt'? y

# SAFE: Use trash-cli instead
$ trash-put /tmp/junk
$ trash-list          # see what is in the trash
$ trash-restore       # recover if needed

2. chmod -R 777 /

DANGER: Destroys All File Security

This command makes every file on the system readable, writable, and executable by every user. It completely destroys the Linux permission model.

What it does

chmod changes file permissions. 777 means read (4) + write (2) + execute (1) for the owner, the group, and everyone else. The -R flag applies this recursively to every file and directory starting from / (the entire system).

# DO NOT RUN THIS - Destroys all security on the system
$ sudo chmod -R 777 /

Why it is dangerous

  • Any user can read, modify, or delete any file, including /etc/passwd, /etc/shadow, system binaries, and configuration files.
  • SSH will refuse to work because it requires strict permissions on key files.
  • sudo may stop working because /etc/sudoers must have specific permissions.
  • Many services (Apache, MySQL, SSH) will refuse to start if their config files have world-writable permissions.
  • The system becomes completely insecure. Any user can install malware, read passwords, or take over the system.
  • Reversing this is nearly impossible because you need to know the correct permissions for every file on the system.

Safe alternatives

# SAFE: Only change permissions on a specific directory you own
$ chmod -R 755 ~/my-project/

# SAFE: Use more restrictive permissions
$ chmod 644 myfile.txt     # Owner read/write, others read only
$ chmod 755 myscript.sh    # Owner full, others read/execute

# SAFE: Only change what you need
$ chmod u+x script.sh      # Add execute only for the owner
Rule of thumb

Never use 777 unless you are doing temporary testing on throwaway files. For web servers, 755 for directories and 644 for files is the standard. Always apply permissions to specific paths, never to /.

3. dd if=/dev/zero of=/dev/sda

EXTREME DANGER: Wipes Entire Disk

This command overwrites your entire hard drive with zeros, destroying the partition table, bootloader, operating system, and all data.

What it does

dd is a low-level tool for copying and converting data. It reads from an input file (if=) and writes to an output file (of=). /dev/zero is a special device that produces an infinite stream of zero bytes. /dev/sda is typically your primary hard drive.

# DO NOT RUN THIS - Overwrites the entire disk with zeros
$ sudo dd if=/dev/zero of=/dev/sda

# Also destructive - writes random data to disk
$ sudo dd if=/dev/urandom of=/dev/sda

Why it is dangerous

  • Directly writes to the raw disk device, bypassing the filesystem entirely.
  • Destroys the partition table, making recovery tools much less effective.
  • Overwrites the bootloader (GRUB), so the system cannot start.
  • There is no confirmation prompt. The moment you press Enter, data is being overwritten.
  • Data recovery after a dd overwrite with zeros is essentially impossible.

When dd is legitimate

dd is a valid tool. It is commonly used to create bootable USB drives and disk images. The danger is writing to the wrong device.

# SAFE: Always triple-check the output device
$ lsblk                              # List all block devices first
NAME   MAJ:MIN RM   SIZE RO TYPE MOUNTPOINT
sda      8:0    0 500.0G  0 disk
├─sda1   8:1    0 499.0G  0 part /
└─sda2   8:2    0   1.0G  0 part [SWAP]
sdb      8:16   1  14.9G  0 disk        <-- USB drive
└─sdb1   8:17   1  14.9G  0 part /media/usb

# SAFE: Write to the USB drive (sdb), NOT the system disk (sda)
$ sudo dd if=ubuntu.iso of=/dev/sdb bs=4M status=progress

# SAFE: Use the status=progress flag to see what is happening
$ sudo dd if=backup.img of=/dev/sdb bs=4M status=progress
Always run lsblk first

Before any dd command, run lsblk to identify your devices. Double-check the output device (of=) is the correct target. One wrong letter (sda instead of sdb) will wipe your system disk.

4. :(){ :|:& };: (Fork Bomb)

DANGER: System Freeze / Denial of Service

This command creates processes that exponentially replicate, consuming all system resources until the system freezes or crashes.

What it does

This cryptic string is a bash function that calls itself twice, with each copy running in the background. Let us break it down:

# DO NOT RUN THIS - Fork bomb explained
# :(){ :|:& };:
#
# :()      - Define a function named ":"
# {        - Start function body
#   :|:    - Call itself and pipe to another copy of itself
#   &      - Run in the background
# };       - End function definition
# :        - Call the function to start the chain

# More readable version (still DO NOT RUN):
bomb() {
  bomb | bomb &
};
bomb

Why it is dangerous

  • Each function call creates two new processes, which each create two more, and so on exponentially: 1, 2, 4, 8, 16, 32, 64...
  • Within seconds, the system runs out of process IDs and memory.
  • The system becomes completely unresponsive. You cannot open a terminal, run kill, or even move the mouse.
  • Usually requires a hard reboot (holding the power button).
  • Does not cause permanent damage, but any unsaved work is lost.

How to protect yourself

# Check current process limits
$ ulimit -u
63451

# Set a per-user process limit (add to /etc/security/limits.conf)
# This limits each user to 500 processes
$ sudo nano /etc/security/limits.conf
*    hard    nproc    500
*    soft    nproc    500

# Temporary limit for current session
$ ulimit -u 500
Be suspicious of cryptic one-liners

If someone in a forum suggests a command that looks like random punctuation, do not run it. Look it up first. Fork bombs are often disguised in obfuscated forms.

5. mkfs.ext4 /dev/sda

EXTREME DANGER: Formats Entire Disk

This command creates a new filesystem on the specified device, destroying all existing data, partitions, and the operating system.

What it does

mkfs (make filesystem) creates a new, empty filesystem on a device. Running it on /dev/sda (your primary disk) destroys the partition table and all data, replacing it with a blank ext4 filesystem.

# DO NOT RUN THIS - Formats your primary disk
$ sudo mkfs.ext4 /dev/sda

# Also dangerous variants:
$ sudo mkfs.xfs /dev/sda
$ sudo mkfs.btrfs /dev/sda
$ sudo mkfs.vfat /dev/sda1

Why it is dangerous

  • Erases all data on the target device or partition.
  • If run on the system disk, the operating system is destroyed.
  • The original partition table is overwritten.
  • Some data recovery may be possible with specialized tools, but it is not guaranteed.

When mkfs is legitimate

# SAFE: Format a NEW, EMPTY USB drive (after confirming device with lsblk)
$ lsblk                               # Verify which device is the USB
$ sudo mkfs.ext4 /dev/sdb1             # Format a specific partition on USB

# SAFE: Always work with partitions (sdb1), not whole devices (sdb)
# SAFE: Always run lsblk and double-check before formatting
The golden rule of mkfs

Always run lsblk and mount before using mkfs. Never format a mounted device. Never format a device without verifying it is the correct target. When in doubt, do not format.

6. > important_file (Truncation)

DANGER: Silently Empties Files

The redirect operator > by itself truncates a file to zero bytes. The data is gone instantly and silently.

What it does

In bash, > filename opens the file for writing, truncating it to zero length. If the file contained 10 GB of important data, it now contains nothing. There is no confirmation, no warning, and no undo.

# DO NOT RUN THIS on important files
$ > /etc/resolv.conf       # DNS configuration gone
$ > ~/.bashrc               # Shell configuration gone
$ > /var/log/syslog         # All logs gone

# How it happens accidentally:
# You meant to APPEND to a log file:
$ echo "entry" >> logfile.txt    # Correct: appends
# But you typed only one >:
$ echo "entry" > logfile.txt     # WRONG: overwrites entire file!

Why it is dangerous

  • The operation is instant and silent. No error message, no confirmation.
  • The original file contents are irrecoverable (unlike rm, there is no "trash" to check).
  • Can happen easily by typing > instead of >>.
  • If done on a critical system file, services may break immediately.

Safe alternatives

# SAFE: Always use >> to append
$ echo "new log entry" >> logfile.txt

# SAFE: Use tee to append (also shows output on screen)
$ echo "new entry" | tee -a logfile.txt

# SAFE: Make a backup before overwriting
$ cp important_file important_file.bak
$ some_command > important_file

# SAFE: Use noclobber to prevent accidental overwrites
$ set -o noclobber
$ echo "test" > existing_file
bash: existing_file: cannot overwrite existing file

# To override noclobber when you really mean it:
$ echo "test" >| existing_file
Enable noclobber in your .bashrc

Add set -o noclobber to your ~/.bashrc file. This prevents > from overwriting any existing file. You can still force an overwrite with >| when you truly intend to.

7. wget url -O- | sh (Running Untrusted Scripts)

DANGER: Executing Unknown Code

Piping a download directly into a shell executes whatever code is at that URL with no review, no confirmation, and potentially with root privileges.

What it does

This pattern downloads a script from the internet and immediately executes it in your shell. You have no chance to inspect what the script does before it runs.

# RISKY patterns - downloading and executing in one step
$ wget http://example.com/setup.sh -O- | sh
$ curl -s http://example.com/install.sh | bash
$ curl http://example.com/script.sh | sudo bash    # Even worse with sudo!

Why it is dangerous

  • You are running code you have never seen. It could do anything: install malware, create backdoors, steal SSH keys, mine cryptocurrency, or delete files.
  • Adding sudo gives the unknown script root access to your entire system.
  • The URL could change at any time. A script that was safe yesterday might be malicious today.
  • Network errors could cause partial downloads, executing an incomplete (and unpredictable) script.
  • Some legitimate software uses this installation method (Docker, Node Version Manager), but you should still verify the source.

Safe alternatives

# SAFE: Download first, review, then execute
$ wget http://example.com/setup.sh -O setup.sh
$ cat setup.sh                  # Read the entire script
$ less setup.sh                 # Or use less for long scripts
$ bash setup.sh                 # Run only after reviewing

# SAFE: Verify checksums if provided
$ wget http://example.com/setup.sh
$ sha256sum setup.sh
a3f5b9c... setup.sh
# Compare the hash with the one published on the official site

# SAFE: Use your distribution's package manager instead
$ sudo apt install docker.io     # Better than curl | bash
Rule: Never pipe to sh with sudo

If any installation instructions tell you to run curl ... | sudo bash, stop and ask yourself: do I trust this source completely? Is there a package manager alternative? Can I download and review the script first?

8. mv file /dev/null

DANGER: File Destroyed Permanently

Moving a file to /dev/null does not "discard the output" like redirecting to it. It destroys the file and replaces /dev/null with it, potentially breaking the system.

What it does

/dev/null is a special device file that discards everything written to it. However, mv does not "write" to a destination — it replaces it. So mv file /dev/null removes the original file and replaces the /dev/null device with a regular file.

# DO NOT RUN THIS
$ mv important_document.pdf /dev/null
# Result: important_document.pdf is gone, AND /dev/null is broken

# This breaks /dev/null because it is no longer a special device file.
# Many programs depend on /dev/null working correctly.

Why it is dangerous

  • Your original file is gone permanently (not in any trash).
  • The /dev/null device node is destroyed and replaced with a regular file.
  • Programs that depend on /dev/null may malfunction until it is recreated.
  • Beginners sometimes think mv file /dev/null is the same as command > /dev/null, but they are completely different operations.

Safe alternatives

# SAFE: Use rm (or trash-put) to delete files
$ rm unwanted_file.txt
$ trash-put unwanted_file.txt    # Even safer - can recover

# SAFE: Redirect output to /dev/null (this is fine)
$ command > /dev/null 2>&1       # Discard stdout and stderr

# If /dev/null was accidentally destroyed, recreate it:
$ sudo rm /dev/null
$ sudo mknod /dev/null c 1 3
$ sudo chmod 666 /dev/null

9. Redirect Mistakes: > vs >>

DANGER: Data Loss from Wrong Redirect

Using > when you meant >> overwrites the file instead of appending to it. All previous contents are lost.

What it does

Bash has two redirect operators for writing to files:

  • > — Overwrite: truncates the file to zero, then writes the new content.
  • >> — Append: keeps all existing content and adds new content at the end.
# Scenario: You have a log file with months of data
$ wc -l application.log
847291 application.log

# You meant to append a new entry:
$ echo "2025-03-31 Maintenance complete" >> application.log   # CORRECT

# But you accidentally typed one > instead of >>:
$ echo "2025-03-31 Maintenance complete" > application.log    # WRONG!

$ wc -l application.log
1 application.log
# 847,291 lines of log data are gone. Only the one new line remains.

Common real-world accidents

# Accident 1: Overwriting /etc/hosts instead of adding an entry
$ echo "192.168.1.100 myserver" > /etc/hosts     # All DNS entries gone!

# Accident 2: Destroying a config file
$ echo "new_setting=true" > ~/.bashrc             # All aliases, paths, config gone!

# Accident 3: Cron job that overwrites instead of appending logs
# In crontab:
# 0 * * * * /usr/local/bin/backup.sh > /var/log/backup.log
# This overwrites the log every hour. Only the last run is kept.

How to protect yourself

# Protection 1: Enable noclobber
$ set -o noclobber
$ echo "test" > existing_file.txt
bash: existing_file.txt: cannot overwrite existing file

# Protection 2: Use tee -a for appending (visual confirmation)
$ echo "new entry" | tee -a logfile.txt
new entry

# Protection 3: Back up before modifying
$ cp /etc/hosts /etc/hosts.bak
$ echo "192.168.1.100 myserver" >> /etc/hosts

# Protection 4: Add noclobber to .bashrc permanently
$ echo 'set -o noclobber' >> ~/.bashrc
Build the habit

When you type a >, stop and ask yourself: "Do I want to overwrite or append?" Make this a conscious check every time. It takes one second and can save hours of recovery work.

Safety Checklist

Before Running Any Destructive Command

Follow this checklist every time you run a command that modifies or deletes files, especially with sudo:

  1. Check your current directory with pwd

    Make sure you are where you think you are. Running rm -rf * in / is very different from running it in /tmp/test.

    $ pwd
/home/user/projects/old-project
# Good - I am in the right place
  2. Use -i (interactive) flags

    Many commands support -i to prompt for confirmation before each action.

    $ rm -ri old-directory/         # Confirm each file deletion
$ cp -i source.txt dest.txt     # Confirm before overwriting
$ mv -i file.txt /other/path/   # Confirm before overwriting
  3. Preview before executing

    Use ls, find, or echo to see what would be affected.

    # See what rm would delete
$ ls *.log
app.log  error.log  debug.log
# Okay, those are the ones I want to remove
$ rm *.log

# Preview find results before deleting
$ find /tmp -name "*.tmp" -mtime +7
/tmp/session_abc123.tmp
/tmp/upload_xyz789.tmp
$ find /tmp -name "*.tmp" -mtime +7 -delete
  4. Use --dry-run where available

    Some commands support --dry-run or -n to show what would happen without actually doing it.

    $ rsync -av --dry-run source/ dest/
sending incremental file list
file1.txt
file2.txt
sent 150 bytes  received 25 bytes  350.00 bytes/sec
(DRY RUN)
  5. Install and use trash-cli

    Replace rm with trash-put so deleted files go to a recoverable trash folder.

    $ sudo apt install trash-cli
$ trash-put unwanted-file.txt     # Moves to trash
$ trash-list                       # See what is in trash
$ trash-restore                    # Recover a file
$ trash-empty                      # Permanently delete trash
  6. Back up important files before modifying them

    A quick cp can save hours of recovery work.

    $ cp /etc/nginx/nginx.conf /etc/nginx/nginx.conf.bak
$ cp ~/.bashrc ~/.bashrc.bak
$ cp -r ~/important-project ~/important-project-backup
  7. Use version control (git) for code and configuration

    If your files are in a git repository, you can always recover any previous version.

    $ cd ~/my-project
$ git add .
$ git commit -m "Backup before major changes"
# Now you can safely experiment. If things go wrong:
$ git checkout -- .              # Restore all files to last commit
  8. Read the man page when unsure

    If you are not 100% sure what a flag does, check the manual first.

    $ man rm
$ rm --help

Protective Shell Aliases

Add these aliases to your ~/.bashrc to add safety nets to common commands:

# Add these lines to ~/.bashrc

# Always ask before overwriting or deleting
alias rm='rm -i'
alias cp='cp -i'
alias mv='mv -i'

# Prevent accidental overwriting with >
set -o noclobber

# Make rm safer with colors showing what is deleted
alias rm='rm -Iv'

# Use trash instead of rm (install trash-cli first)
alias del='trash-put'

# Always show what chmod/chown is changing
alias chmod='chmod -v'
alias chown='chown -v'

# Confirm before running dd
# (dd does not have a -i flag, so use a function)
safe_dd() {
  echo "WARNING: You are about to run dd with these arguments:"
  echo "  dd $@"
  echo ""
  read -p "Are you sure? (yes/no): " confirm
  if [ "$confirm" = "yes" ]; then
    command dd "$@"
  else
    echo "Aborted."
  fi
}
alias dd='safe_dd'

rm -rf * Deletes all in current dir ls * first, then rm -ri *

dd if=/dev/zero of=/dev/sda Wipes entire disk lsblk first, target specific partition

What To Do If You Already Ran Something Dangerous

Stay calm and assess the damage

If you accidentally ran a destructive command, follow these steps:

  1. Stop immediately. Press Ctrl+C to interrupt the command if it is still running. Every second matters.
  2. Do not reboot yet. If files were deleted but the system is still running, programs in memory may still work. Rebooting could make things worse.
  3. Assess what was affected. Check which files are missing or changed.
  4. Check backups. Do you have recent backups? Cloud storage? Git repositories? Another copy somewhere?
  5. For deleted files: Tools like testdisk, photorec, or extundelete may recover some data, but this is not guaranteed. The sooner you act, the better the chances.
  6. For permission changes: If you ran chmod -R 777 on a large part of the system, reinstalling may be the fastest fix. Manually restoring permissions for thousands of system files is extremely tedious.
  7. For formatted drives: Do not write anything more to the drive. Use a live USB to boot and attempt recovery with testdisk.
  8. Learn from it. Set up the safety measures described on this page so it does not happen again.
# Emergency: Try to recover deleted files (from a live USB)
$ sudo apt install testdisk
$ sudo testdisk /dev/sda

# Emergency: Recover specific file types (photos, documents)
$ sudo apt install photorec
$ sudo photorec /dev/sda
Prevention is always better than recovery

Data recovery is unreliable, expensive, and time-consuming. The best protection is to never run dangerous commands in the first place, and to maintain regular backups of everything important. Set up automated backups today — do not wait until you need them.

Knowledge Check

For each scenario, identify the risk and the safe alternative:

  1. Your coworker tells you to run sudo rm -rf /tmp /old-logs. What should you check first?
  2. A tutorial says to run curl -sS https://example.com/install | sudo bash. What is the safer approach?
  3. You need to clear a log file but keep the file itself. How do you do it safely?
Show Answers
  1. Check for accidental spaces: is it /tmp/old-logs (one path) or /tmp /old-logs (two paths, where /tmp would be deleted entirely)? Also verify you want the -rf flags. Run ls /tmp/old-logs first to see what is there.
  2. Download the script first: curl -sS https://example.com/install -o install.sh, then read it with less install.sh, and only run it after reviewing: bash install.sh.
  3. Use truncate -s 0 logfile.log or : > logfile.log (with noclobber disabled). Both empty the file while keeping it intact. Back up first if the log data might be needed.
